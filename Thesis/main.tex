\section{Analýza dostupných služeb AWS}
Amazon Web Services (AWS) je jedním ze současným největších poskytovatelů cloudových služeb na trhu. Nabízí širokou škálu služeb, které umožňují vytváření a provozování škálovatelných a spolehlivých aplikací. Z tohoto obrovského množství služeb musíme vybrat relevantní podmnožinu pro daný problém.

\subsection{AWS Elastic Compute Cloud}
Elastic Compute Cloud, zkráceně EC2, je základní služba AWS, která poskytuje škálovatelné výpočetní kapacity v cloudu ve formě virtuálních serverů neboli instancí. Každá instance slouží jako samostatný virtuální stroj, který si uživatel spravuje dle svých potřeb. EC2 podporuje různé operačních systémy, včetně různých distribucí Linuxu a Windows Serveru. Uživatelé mohou také vytvářet vlastní Amazon Machine Images (AMI), která obsahují předkonfigurované prostředí pro specifické aplikace. Je zřejmé, že EC2 nespadá pod serverless computing, neboť uživatel je zodpovědný za správu instancí.

Jelikož se jedná o centrální službu, můžeme v AWS najít mnoho dalších způsobů konfigurace EC2 instancí i služeb s nimi spojených, jako například automatické škálování, load balancing, nebo služby pro správu virtuální sítě.

Pro účely monitorovacího systému je možné na EC2 instancích provozovat vlastní Zabbix server a proxy, ale také případně provozovat software sloužící jako prostředník mezi AWS a Zabbix proxy.

\subsection{AWS Lambda}
AWS Lambda funkcím, jakožto hlavní službě této práce, věnujme v této sekci intenzivní pozornost. Jedná se implementaci FaaS paradigmatu v AWS s podporou pro mnoho vývojářských prostředí (různé programovací jazyky a Docker kontejnery). Programátor poskytne kód funkce\footnote{Reálně se nemusí jednat o jednu proceduru programovacího jazyka, může být poskytnut malý program} se vstupním bodem implementujícím rozhraní specifikované pro dané prostředí (hlavička vstupní procedury) a AWS se postará o její nasazení, běh a škálování. Lambda funkce jsou spouštěny na základě uživatelem specifikovaných událostí, například voláním AWS API pomocí nástroje z příkazové řádky, událostí generovanou jinou AWS službou (S3, FireHose, SQS...), nebo na základě časovače \cite{lambda.docs.aws}. Uživateli je účtováno pouze za čas, po který je funkce spuštěna, za využití paměti a za počet požadavků (spuštění funkce) \cite{lambda.pricing.aws}.

\subsubsection{Vývoj Lambda funkcí}
Vývoj Lambda funkcí je možný v několika programovacích jazycích, mezi které patří Python, Node.js, Java, Go, Ruby, C\# a PowerShell. Vstupní bod funkce, neboli \uv{handler}, musí implementovat požadované rozhraní, které se konkrétně mění pro každý jazyk dle dokumentace (např. funkce pro Python, Node.js nebo třída implementující rozhraní v jazyce Java), avšak všechny mají společný tvar -- přijímají dva argumenty, událost (event) a kontext (context), a vrací výsledek typicky ve formátu JSON. Událost obsahuje vstupní data funkce, poskytnutá volajícím, tedy např. uživatelem invokujícím Lambda funkci z příkazové řádky nebo AWS službou (formát pak odpovídá specifikaci dané služby\footnote{U některých služeb však formát události není v dokumentaci uveden... Viz dále.}). Kontext je zpravidla objekt obsahující informace o běhu funkce, jako například velikost paměti, čas spuštění, nebo identifikátor požadavku (volání) \cite{lambda.docs.aws}.

Kód funkce je možné nahrát do AWS více způsoby: při vytváření funkce v grafickém rozhraní AWS (AWS Management Console), pomocí nástroje SAM, krátké funkce přímo v šabloně CloudFormation atp. Program se uloží do komprimovaného archivu ve formátu ZIP do automaticky vytvořeného S3 bucketu. Složitější funkce, které vyžadují větší množství souborů a závislostí, je třeba nahrát do S3 bucketu ručně a poté vytvořit funkci s odkazem na tento bucket, anebo je možné využít zmíněného nástroje SAM, jehož cílem je zjednodušit nasazení serverless aplikací v AWS \cite{sam.docs.aws, lambda.docs.aws}. Závislosti, soubory anebo vlastní výpočetní prostředí sdílené více funkcemi je také možné poskytnout jako tzv. vrstvu (layer) ve vlastním ZIP archivu, na niž se Lambda funkce odkazují. Některé závislosti jsou dostupné přímo v AWS Lambda prostředí, zejména knihovny pro práci s AWS službami (AWS SDK) \cite{lambda.docs.aws}.

Kromě archivu umožňuje AWS poskytnout funkci jako Docker image, ač je v takovém případě nutno poskytnout program implementující REST API rozhraní zprostředkující komunikaci mezi kontejnerem a službou AWS Lambda\footnote{vývojáři AWS však připravili několik Docker image, na nichž je možno stavět Lambda funkce, které takový program obsahují}. U Docker image navíc nejsou podporovány vrstvy \cite{lambda.docs.aws}.

\subsubsection{Invokace Lambda funkcí}
Dokumentace AWS Lambda specifikuje různé způsoby, jak může být funkce spuštěna. Základní rozdělení definuje synchronní a asynchronní volání, přičemž synchronní volání je \uv{blokující} a vrací výsledek volání, zatímco asynchronní volání vloží vstup do fronty událostí v AWS a na výstup nečeká, zahazuje jej. Oba typy volání je možné provést pomocí AWS Management Console, AWS CLI, SDK nebo API. Maximální velikost vstupních dat je omezena na 6 MB \cite{lambda.docs.aws}.

Lambda funkce je možné integrovat s dalšími službami AWS, které invokují funkce automaticky. Integraci uživatel realizuje při konfiguraci služby, kterou plánuje využívat. Různé služby mouhou funkce volat synchronně nebo asynchronně dle dokumentace. V tomto případě invokací však dochází k dalšímu dělení na \uv{triggered} a \uv{event source mapping} invokace. Některé služby volají Lambda funkce ze své strany pomocí triggerů, poskytujíce vstupní data samy, kdežto zejména streamovací služby (např. Kinesis, DynamoDB) využívají event source mapping, zdroj na straně AWS Lambda, držící tzv. \uv{event poller} komponenty, které získávají dávky událostí (vstupních dat) ze zdrojové služby a posílají je do cílové Lambda funkce. Cílem event source mapping je zpracování velkého množství dat v jednom volání funkce a v důsledku zvýšení propustnosti oproti volání Lambda funkce pro každou položku ve streamu. Velikost dávky je dále možné konfigurovat podle počtu událostí v dávce a doby trvání sběru událostí do jedné dávky a také podléhá omezení na 6 MB \cite{lambda.docs.aws}.

\subsubsection{Škálování a konkurentnost}
AWS Lambda automaticky (horizontálně) škáluje volání funkcí podle počtu požadavků, nad nimiž je funkce volána. Každá funkce běží v izolovaném prostředí vyhrazeném pouze pro ni. Před prvním voláním je ze strany AWS nutné prostředí připravit (\uv{init} fáze) a až následně může funkce zpracovávat požadavky. Prostředí je udržováno po určitou dobu po posledním volání, aby bylo možné funkci spustit rychleji nad budoucími invokacemi. Při vhodném časování doby běhu funkce a příchody požadavků je tedy možné, že veškeré požadavky budou zpracovány v jednom prostředí. Běžně ale nastávají situace, kdy do funkce přichází více požadavků, než je jedna instance schopna odbavit a je třeba funkci spouštět konkurentně.

Konkurentnost (Concurrency) je v AWS dokumentaci chápána jednak jako veličina a jednak jako počet prostředí vyhrazených pro uživatelovy Lambda funkce. Standardní horní limit konkurentnosti je ze strany AWS nastaven na 1000, což prakticky také znamená, že v jeden moment je umožněn běh maximálně 1000 funkcí (v účtu na region). V základním nastavení je tato konkurentnost sdílena mezi všechny funkce v účtu, ale je možné ji nastavit i pro jednotlivé funkce a to dvojím způsobem. Každá funkce může mít nastaven počet \uv{vyhrazené} (reserved) konkurentnosti a \uv{nasazené} (provisioned) konkurentnosti. Vyhrazená konkurentnost udává počet volných a vyhrazených prostředí pro danou funkci, omezujíc tak sdílenou konkurentnost, zároveň ale tento počet shora limituje: funkce nemůže běžet ve více prostředích, než je specifikováno tímto parametrem, a nemůže tedy využívat zbývající sdílenou konkurentnost.

Nasazená konkurentnost je podobná vyhrazené s tím rozdílem, že udává počet \emph{již připravených} prostředí. Při zvýšení (v mezích nasazené konkurentnosti) skutečné konrkurentnosti funkce tak není třeba nové prostředí inicializovat, jelikož již připravené je. U Lambda funkcí je možné nastavit obě konkurentnosti nezávisle, avšak specifikace obou zároveň má smysl pouze v případě, kdy vyhrazená je vyšší než nasazená.

Jestliže funkce vyčerpá svou konkurentnost nebo je vyčerpána sdílená konkurntnost nenastavenými funkcemi, nové požadavky mohou být odmítnuty a zahozeny. Tento jev se nazývá throttling. Navíc AWS nedovoluje omezit sdílenou konkurentnost pod hodnotu 100.

Hodnotu očekávané konkurentnosi $C_f$ funkce $f$ je možné zjistit ze vzathu

$$C_f = \pi_f \cdot \delta_f, $$

kde $\pi_f$ je očekávaný počet požadavků za sekundu a $\delta_f$ je očekávaná doba trvání funkce v sekundách. 

\subsubsection{Verzování}
Lambda umožňuje pro potřeby kontinuálního vývoje funkce verzovat. Funkce je možné vyvíjet/upravovat a testovat ještě před zveřejněním a následně publikovat novou verzi, která je dostupná pro volání. Zveřejněné verze obdrží unikátní monotónně se zvyšující identifikátor a nejde je dále měnit. Konkrétní verze mohou být označeny aliasy sloužícími k přesměrování volání. Aliasy je možné přesměrovat pro plynulý přechod mezi verzemi funkce. AWS navíc umožňujě definovat \emph{vážený alias}, který umožňuje rozdělit provoz mezi dvěmi verzemi podle zadaného poměru, jako podporu \emph{canary deployment} pro účely CI/CD \cite{lambda.docs.aws}.

\subsection{AWS CloudWatch}
% metriky, logy, granularita, alarmy, metric streams + FireHose
Další analyzovanou službou nechť je AWS CloudWatch. Jedná se o službu pro monitorování a logování v AWS, která umožňuje sledovat metriky a výpisy (logy) z různých zdrojů, jako jsou například EC2 instance, Lambda funkce, nebo S3 buckety. Metriky jsou číselné hodnoty, které měří výkon služeb AWS a zdrojů, které jsou s nimi spojeny. Metriky jsou agregovány do tzv. \uv{statistik}, které mohou být zobrazeny v grafu na výchozí nebo vlastní \uv{nástěnce} (dashboard) nebo použity pro vytváření alarmů, konfigurovatelných notifikací zasílaných při dosažení určité hodnoty zvolené statistiky \cite{cloudwatch.docs.aws}. Je zřejmé, že CloudWatch bude stěžejní službou pro vyvíjený systém, neboť poskytuje veškeré potřebné informace pro monitorování Lambda funkcí. Hlavním cílem práce je dopravit tyto informace (resp. jejich konfigurovatelnou podmnožinu) do interního monitorovacího systému Zabbix.

Jelikož naším hlavním zájmem jsou Lambda funkce, budeme se v této sekci dále zaměřovat pouze na možnosti monitorování těchto funkcí v rámci CloudWatch.

\subsubsection{Metriky Lambda funkcí}
Metrika je z pohledu CloudWatch pojmenovaná časově seřazená množina hodnot nějaké proměnné, například využití CPU (u EC2 instancí) nebo doba výpočtu Lambda funkce. CloudWatch dělí metriky do tzv. jmenných prostorů (Namespaces), které slouží k organizaci metrik, zajištění jednoznačnosti jejich názvů a izolaci. Každá monitorovatelná AWS služba má svůj vyhrazený Namespace, pro Lambda funkce je to \texttt{AWS/Lambda}, a další jmenné prostory může definovat uživatel. 

Kromě jmenného prostoru a názvu jsou metriky definovány ještě \emph{dimezemi}. Dimenze je dvojice název-hodnota přidávající další identitu dané metrice. Názvy dimenzí jsou kategorie, do nichž může metrika patřit, například jméno Lambda funkce, verze, nebo region, ve kterém je funkce spuštěna. Hodnoty dimenzí jsou konkrétní instance těchto kategorií, které od sebe oddělují metriky. Metrika může mít až 30 dimenzí (nebo žádnou). Dimenze se dají libovolně kombinovat a hodnota metriky se uloží pouze pro danou kombinaci dimenzí. Monitorovatelné služby definují vlastní dimenze a narozdíl od uživatelsky definovaných dimenzí je služba AWS CloudWatch schopna agregovat hodnoty z vynechaných dimenzí \cite{cloudwatch.docs.aws}. Lambda funkce definují dimenze pro název funkce, \uv{zdroj} (resource), pod niž spadají verze a aliasy funkcí a další. Vyvíjený systém má dle požadavků zákazníka monitorovat metriky pro jednotlivé funkce bez odlišování verzí -- metriky pro danou funkci tak budou obsahovat údaje ze všech verzí funkce.

CloudWatch všechny metriky agreguje do statistik, které mohou být zobrazeny v grafu nebo použity pro vytváření alarmů, z hodnot metrik za určitý časový interval. Poskytované statistiky jsou například průměr, maximum a minimum, suma, počet hodnot nebo některé percentily \cite{cloudwatch.docs.aws}.

Služba AWS Lambda zaznamenává mnoho metrik a dělí je na několik druhů. Některé z nich jsou:

\begin{itemize}
    \item metriky invokací
    \begin{itemize}
        \item \texttt{Invocations} -- počet invokací funkce
        \item \texttt{Errors} -- počet selhaných invokací
        \item \texttt{DeadLetterErrors} -- počet selhaných pokusů o zápis do Dead Letter Queue asynchronními invokacemi
    \end{itemize}
    \item metriky výkonu
    \item metriky konkurentnosi
    \item metriky asynchronních invokací
    \item metriky event source mapping
\end{itemize}
