\section{Analýza dostupných služeb AWS}
Amazon Web Services (AWS) je jedním ze současným největších poskytovatelů cloudových služeb na trhu. Nabízí širokou škálu služeb, které umožňují vytváření a provozování škálovatelných a spolehlivých aplikací. Z tohoto obrovského množství služeb musíme vybrat relevantní podmnožinu pro daný problém.

\subsection{AWS Elastic Compute Cloud}
Elastic Compute Cloud, zkráceně EC2, je základní služba AWS, která poskytuje škálovatelné výpočetní kapacity v cloudu ve formě virtuálních serverů neboli instancí. Každá instance slouží jako samostatný virtuální stroj, který si uživatel spravuje dle svých potřeb. EC2 podporuje různé operačních systémy, včetně různých distribucí Linuxu a Windows Serveru. Uživatelé mohou také vytvářet vlastní Amazon Machine Images (AMI), která obsahují předkonfigurované prostředí pro specifické aplikace. Je zřejmé, že EC2 nespadá pod serverless computing, neboť uživatel je zodpovědný za správu instancí.

Jelikož se jedná o centrální službu, můžeme v AWS najít mnoho dalších způsobů konfigurace EC2 instancí i služeb s nimi spojených, jako například automatické škálování, load balancing, nebo služby pro správu virtuální sítě.

Pro účely monitorovacího systému je možné na EC2 instancích provozovat vlastní Zabbix server a proxy, ale také případně provozovat software sloužící jako prostředník mezi AWS a Zabbix proxy.

\subsection{AWS Lambda}
AWS Lambda funkcím, jakožto hlavní službě této práce, věnujme v této sekci intenzivní pozornost. Jedná se implementaci FaaS paradigmatu v AWS s podporou pro mnoho vývojářských prostředí (různé programovací jazyky a Docker kontejnery). Programátor poskytne kód funkce\footnote{Reálně se nemusí jednat o jednu proceduru programovacího jazyka, může být poskytnut malý program} se vstupním bodem implementujícím rozhraní specifikované pro dané prostředí (hlavička vstupní procedury) a AWS se postará o její nasazení, běh a škálování. Lambda funkce jsou spouštěny na základě uživatelem specifikovaných událostí, například voláním AWS API pomocí nástroje z příkazové řádky, událostí generovanou jinou AWS službou (S3, Firehose, SQS...), nebo na základě časovače \cite{lambda.docs.aws}. Uživateli je účtováno pouze za čas, po který je funkce spuštěna, za využití paměti a za počet požadavků (spuštění funkce) \cite{lambda.pricing.aws}.

\subsubsection{Vývoj Lambda funkcí}
Vývoj Lambda funkcí je možný v několika programovacích jazycích, mezi které patří Python, Node.js, Java, Go, Ruby, C\# a PowerShell. Vstupní bod funkce, neboli \uv{handler}, musí implementovat požadované rozhraní, které se konkrétně mění pro každý jazyk dle dokumentace (např. funkce pro Python, Node.js nebo třída implementující rozhraní v jazyce Java), avšak všechny mají společný tvar -- přijímají dva argumenty, událost (event) a kontext (context), a vrací výsledek typicky ve formátu JSON. Událost obsahuje vstupní data funkce, poskytnutá volajícím, tedy např. uživatelem invokujícím Lambda funkci z příkazové řádky nebo AWS službou (formát pak odpovídá specifikaci dané služby\footnote{U některých služeb však formát události není v dokumentaci uveden... Viz dále.}). Kontext je zpravidla objekt obsahující informace o běhu funkce, jako například velikost paměti, čas spuštění, nebo identifikátor požadavku (volání) \cite{lambda.docs.aws}.

Kód funkce je možné nahrát do AWS více způsoby: při vytváření funkce v grafickém rozhraní AWS (AWS Management Console), pomocí nástroje SAM, krátké funkce přímo v šabloně CloudFormation atp. Program se uloží do komprimovaného archivu ve formátu ZIP do automaticky vytvořeného S3 bucketu. Složitější funkce, které vyžadují větší množství souborů a závislostí, je třeba nahrát do S3 bucketu ručně a poté vytvořit funkci s odkazem na tento bucket, anebo je možné využít zmíněného nástroje SAM, jehož cílem je zjednodušit nasazení serverless aplikací v AWS \cite{sam.docs.aws, lambda.docs.aws}. 

Závislosti, soubory anebo vlastní výpočetní prostředí sdílené více funkcemi je možné poskytnout jako tzv. vrstvu (layer) ve vlastním ZIP archivu, na niž se Lambda funkce odkazují. Některé závislosti jsou dostupné přímo v AWS Lambda prostředí, zejména knihovny pro práci s AWS službami (AWS SDK). Mimo vrstvy je také k funkcím možno připojit rozšíření (extension), dodané také jako ZIP archiv. Rozšíření mohou být externí, běžící jako nezávislý proces uvnitř výpočetního prostředí, anebo interní jako vlákno procesu řídícího Lambda funkci. AWS Lambda poskytuje některá již hotová rozšíření, zejména od partnerů třetích stran, mnoho z nichž se orientují právě na monitoring, observability a bezpečnost. Zabbix se však mezi partnery nevyskytuje \cite{lambda.docs.aws}.

Kromě archivu umožňuje AWS poskytnout funkci jako Docker image, ač je v takovém případě nutno poskytnout program implementující REST API rozhraní zprostředkující komunikaci mezi kontejnerem a službou AWS Lambda\footnote{vývojáři AWS však připravili několik Docker image, na nichž je možno stavět Lambda funkce, které takový program obsahují}. U Docker image navíc nejsou podporovány vrstvy \cite{lambda.docs.aws}.

\subsubsection{Invokace Lambda funkcí}
Dokumentace AWS Lambda specifikuje různé způsoby, jak může být funkce spuštěna. Základní rozdělení definuje synchronní a asynchronní volání, přičemž synchronní volání je \uv{blokující} a vrací výsledek volání, zatímco asynchronní volání vloží vstup do fronty událostí v AWS a na výstup nečeká, zahazuje jej. Oba typy volání je možné provést pomocí AWS Management Console, AWS CLI, SDK nebo API. Maximální velikost vstupních dat je omezena na 6 MB \cite{lambda.docs.aws}.

Lambda funkce je možné integrovat s dalšími službami AWS, které invokují funkce automaticky. Integraci uživatel realizuje při konfiguraci služby, kterou plánuje využívat. Různé služby mouhou funkce volat synchronně nebo asynchronně dle dokumentace. V tomto případě invokací však dochází k dalšímu dělení na \uv{triggered} a \uv{event source mapping} invokace. Některé služby volají Lambda funkce ze své strany pomocí triggerů, poskytujíce vstupní data samy, kdežto zejména streamovací služby (např. Kinesis, DynamoDB) využívají event source mapping, zdroj na straně AWS Lambda, držící tzv. \uv{event poller} komponenty, které získávají dávky událostí (vstupních dat) ze zdrojové služby a posílají je do cílové Lambda funkce. Cílem event source mapping je zpracování velkého množství dat v jednom volání funkce a v důsledku zvýšení propustnosti oproti volání Lambda funkce pro každou položku ve streamu. Velikost dávky je dále možné konfigurovat podle počtu událostí v dávce a doby trvání sběru událostí do jedné dávky a také podléhá omezení na 6 MB \cite{lambda.docs.aws}.

\subsubsection{Škálování a konkurentnost}
AWS Lambda automaticky (horizontálně) škáluje volání funkcí podle počtu požadavků, nad nimiž je funkce volána. Každá funkce běží v izolovaném prostředí vyhrazeném pouze pro ni. Před prvním voláním je ze strany AWS nutné prostředí připravit (\uv{init} fáze) a až následně může funkce zpracovávat požadavky. Prostředí je udržováno po určitou dobu po posledním volání, aby bylo možné funkci spustit rychleji nad budoucími invokacemi. Při vhodném časování doby běhu funkce a příchody požadavků je tedy možné, že veškeré požadavky budou zpracovány v jednom prostředí. Běžně ale nastávají situace, kdy do funkce přichází více požadavků, než je jedna instance schopna odbavit a je třeba funkci spouštět konkurentně.

Konkurentnost (Concurrency) je v AWS dokumentaci chápána jednak jako veličina a jednak jako počet prostředí vyhrazených pro uživatelovy Lambda funkce. Standardní horní limit konkurentnosti je ze strany AWS nastaven na 1000, což prakticky také znamená, že v jeden moment je umožněn běh maximálně 1000 funkcí (v účtu na region). V základním nastavení je tato konkurentnost sdílena mezi všechny funkce v účtu, ale je možné ji nastavit i pro jednotlivé funkce a to dvojím způsobem. Každá funkce může mít nastaven počet \uv{vyhrazené} (reserved) konkurentnosti a \uv{nasazené} (provisioned) konkurentnosti. Vyhrazená konkurentnost udává počet volných a vyhrazených prostředí pro danou funkci, omezujíc tak sdílenou konkurentnost, zároveň ale tento počet shora limituje: funkce nemůže běžet ve více prostředích, než je specifikováno tímto parametrem, a nemůže tedy využívat zbývající sdílenou konkurentnost.

Nasazená konkurentnost je podobná vyhrazené s tím rozdílem, že udává počet \emph{již připravených} prostředí. Při zvýšení (v mezích nasazené konkurentnosti) skutečné konrkurentnosti funkce tak není třeba nové prostředí inicializovat, jelikož již připravené je. U Lambda funkcí je možné nastavit obě konkurentnosti nezávisle, avšak specifikace obou zároveň má smysl pouze v případě, kdy vyhrazená je vyšší než nasazená.

Jestliže funkce vyčerpá svou konkurentnost nebo je vyčerpána sdílená konkurntnost nenastavenými funkcemi, nové požadavky mohou být odmítnuty a zahozeny. Tento jev se nazývá throttling. Navíc AWS nedovoluje omezit sdílenou konkurentnost pod hodnotu 100.

Hodnotu očekávané konkurentnosi $C_f$ funkce $f$ je možné zjistit ze vzathu

$$C_f = \pi_f \cdot \delta_f, $$

kde $\pi_f$ je očekávaný počet požadavků za sekundu a $\delta_f$ je očekávaná doba trvání funkce v sekundách. 

\subsubsection{Verzování}
Lambda umožňuje pro potřeby kontinuálního vývoje funkce verzovat. Funkce je možné vyvíjet/upravovat a testovat ještě před zveřejněním a následně publikovat novou verzi, která je dostupná pro volání. Zveřejněné verze obdrží unikátní monotónně se zvyšující identifikátor a nejde je dále měnit. Konkrétní verze mohou být označeny aliasy sloužícími k přesměrování volání. Aliasy je možné přesměrovat pro plynulý přechod mezi verzemi funkce. AWS navíc umožňujě definovat \emph{vážený alias}, který umožňuje rozdělit provoz mezi dvěmi verzemi podle zadaného poměru, jako podporu \emph{canary deployment} pro účely CI/CD \cite{lambda.docs.aws}.

\subsection{AWS Simple Storage Service}
Další významnou službou AWS je Simple Storage Service, zkráceně S3. Jedná se o službu pro ukládání a správu dat v cloudu. S3 je vhodné pro ukládání velkého množství dat, jako jsou například statické webové stránky, zálohování, nebo multimediální soubory. S3 nabízí různé třídy úložišť podle předpokládané frekvence přístupu a širokou škálu funkcí, jako je šifrování, správa přístupových práv nebo verze souborů. Mnoho dalších služeb AWS integruje S3 pro své účely. Základní přístup k S3 je přes REST API, ale AWS poskytuje i SDK pro mnoho programovacích jazyků. Další možností je využití tzv. \emph{přístupových bodů} (access points) pro jednodušší a konfigurovatelný přístup k datům \cite{s3.docs.aws}.

Data jsou v S3 ukládána jako \emph{objekty}, soubory s metadaty popisujícími vlastnosti souboru, do kontejnerů zvaných \emph{buckety}. Buckety se dělí do dvou druhů: General purpose buckets (pro obecné účely) a Directory buckets (adresářové), kde první druh ukládá objekty s unikátním názvem (klíčem) v ploché struktuře, kdežto druhý spravuje objekty hierarchicky v adresářové strukutře. Objekt je pak identifikován bucketem, unikátním klíčem (vč. cesty u adresářových bucketů) a případně verzí.

Simple Storage Service využívá silný konzistenční model \todo{teorie ke konzistenčním modelům} \emph{read-after-write}; všechny čtecí operace vracejí hodnotu poslední dokončené zapisovací operace, u konkurentních zápisů však není jisté, který z nich \uv{vyhraje}. AWS S3 používá sémantiku \emph{last-writer-wins}, tedy poslední zápis má přednost, avšak kvůli nespolehlivosti sítě není možné určit, který konkurentní zápis dorazí jako poslední \cite{s3.docs.aws}.

AWS S3 je možné integrovat s AWS Lambda funkcemi a to několika způsoby. Jedním je využití S3 Object Lambda, umožnující transformovat data vrácená čtecími požadavky na objekty S3 pomocí specializovaných přístupových bodů. Požadavek na objekt je přesměrován na standardní přístupový bod, jehož výstup je zpracován poskytnutou Lambda funkcí a následně zaslán klientovi \cite{s3.docs.aws}. Další možností je zasílání notifikací o změnách S3 objektů (např. vytvoření/odstranění). Po dokončení změny objektu služba S3 asynchronně invokuje (triggered invokace) zaregistrované Lambda funkce se vstupem popisujícím událost \cite{lambda.docs.aws}. Funkce pak může na změnu libovolně reagovat.

\subsection{AWS CloudWatch}
% metriky, logy, granularita, alarmy, metric streams + FireHose
Další analyzovanou službou nechť je AWS CloudWatch. Jedná se o službu pro monitorování a logování v AWS, která umožňuje sledovat metriky a výpisy (logy) z různých zdrojů, jako jsou například EC2 instance, Lambda funkce, nebo S3 buckety. Metriky jsou číselné hodnoty, které měří výkon služeb AWS a zdrojů, které jsou s nimi spojeny. Metriky jsou agregovány do tzv. \uv{statistik}, které mohou být zobrazeny v grafu na výchozí nebo vlastní \uv{nástěnce} (dashboard) nebo použity pro vytváření alarmů, konfigurovatelných notifikací zasílaných při dosažení určité hodnoty zvolené statistiky \cite{cloudwatch.docs.aws}. Je zřejmé, že CloudWatch bude stěžejní službou pro vyvíjený systém, neboť poskytuje veškeré potřebné informace pro monitorování Lambda funkcí. Hlavním cílem práce je dopravit tyto informace (resp. jejich konfigurovatelnou podmnožinu) do interního monitorovacího systému Zabbix.

Jelikož naším hlavním zájmem jsou Lambda funkce, budeme se v této sekci dále zaměřovat pouze na možnosti monitorování těchto funkcí v rámci CloudWatch.

\subsubsection{Metriky Lambda funkcí}
Metrika je z pohledu CloudWatch pojmenovaná časově seřazená množina hodnot nějaké proměnné, například využití CPU (u EC2 instancí) nebo doba výpočtu Lambda funkce. CloudWatch dělí metriky do tzv. jmenných prostorů (Namespaces), které slouží k organizaci metrik, zajištění jednoznačnosti jejich názvů a izolaci. Každá monitorovatelná AWS služba má svůj vyhrazený Namespace, pro Lambda funkce je to \texttt{AWS/Lambda}, a další jmenné prostory může definovat uživatel. 

Kromě jmenného prostoru a názvu jsou metriky definovány ještě \emph{dimezemi}. Dimenze je dvojice název-hodnota přidávající další identitu dané metrice. Názvy dimenzí jsou kategorie, do nichž může metrika patřit, například jméno Lambda funkce, verze, nebo region, ve kterém je funkce spuštěna. Hodnoty dimenzí jsou konkrétní instance těchto kategorií, které od sebe oddělují metriky. Metrika může mít až 30 dimenzí (nebo žádnou). Dimenze se dají libovolně kombinovat a hodnota metriky se uloží pouze pro danou kombinaci dimenzí. Monitorovatelné služby definují vlastní dimenze a narozdíl od uživatelsky definovaných dimenzí je služba AWS CloudWatch schopna agregovat hodnoty z vynechaných dimenzí \cite{cloudwatch.docs.aws}. 

CloudWatch všechny metriky agreguje do statistik, které mohou být zobrazeny v grafu nebo použity pro vytváření alarmů, z hodnot metrik za určitý časový interval. Poskytované statistiky jsou například průměr, maximum a minimum, suma, počet hodnot nebo některé percentily \cite{cloudwatch.docs.aws}.

Služba AWS Lambda zaznamenává mnoho metrik a dělí je na několik druhů. Některé z nich jsou \cite{lambda.docs.aws}:

\begin{itemize}
    \item metriky invokací -- příznakové binární metriky, pro něž má smysl pouze statistika součtu
    \begin{itemize}
        \item \texttt{Invocations} -- počet invokací funkce
        \item \texttt{Errors} -- počet selhaných invokací
        \item \texttt{DeadLetterErrors} -- počet selhaných pokusů o zápis do Dead Letter Queue asynchronními invokacemi
        \item \texttt{Throttles} -- počet odmítnutých invokací kvůli nedostatku konkurentnosti
    \end{itemize}
    \item metriky výkonu
    \begin{itemize}
        \item \texttt{Duration} -- doba trvání funkce, podporuje kvantilové statistiky
        \item \texttt{IteratorAge} -- věk nejstaršího zpracovávaného záznamu v události vzniklé při event source mapping pro Kinesis stream
    \end{itemize}
    \item metriky konkurentnosi
    \begin{itemize}
        \item \texttt{ConcurrentExecutions} -- počet současně běžících instancí funkce
        \item \texttt{UnreservedConcurrentExecutions} -- počet současně běžících instancí funkce, které není vyhrazena konkurentnost
        \item \texttt{ClaimedAccountConcurency} -- počet spuštěných prostředí (využitá konkurentnost)
    \end{itemize}
\end{itemize}

Z výpisu je zřejmé, že ne všechny metriky se týkají přímo Lambda funkcí, některé monitorují jiné činnosti služby AWS Lambda. Například metrika \texttt{ClaimedAccountConcurency} znázorňuje využitou konkurentnost v účtu a regionu skrz všechny funkce. Dle zadání práce je třeba umožnit monitorování pouze metrik přímo souvisejících s funkcemi, dále tedy pracujme pouze v jejich kontextu. 

Všechny takové metriky definují dimenze pro název funkce, \uv{zdroj} (resource), pod niž spadají verze a aliasy funkce, a některé další. Dokumentace tuto skutečnost dopodrobna nerozvíjí a pouze se letmo o dimenzích metrik pro AWS Lambda zmiňuje, a tak byl tento poznatek zjištěn experimentálně\footnote{Během vývoje ve zkušebním stavu, kdy byl zkoumán formát požadavků do transformační Lambda funkce z Data Firehose se zdrojem v Metric streamu, viz dále.}. Vyvíjený systém má dle požadavků zákazníka monitorovat metriky pro jednotlivé funkce bez odlišování verzí, což prakticky znamená, že bude třeba exportovat metriky pouze s dimenzí názvu funkce. AWS Lambda do těchto metrik automaticky agreguje i hodnoty pro všechny verze a aliasy funkce s daným názvem, jak bylo poznamenáno výše.

\subsubsection{Metric Stream}
V této fázi analýzy již známe dostatek o poskytovaných metrikách Lambda funkcí, dále bude potřeba najít způsob, jak je dostat do externího systému Zabbix. Možností se nabízí spousta, například periodické volání AWS API v procesu nové EC2 instance nebo ve vyhrazené Lambda funkci, vývoj exportovací procedury/knihovny, její připojení k monitorovaným funkcím v nové vrstvě a následné volání z kódu nebo připojení vlastního rozšíření Lambda funkce sbírajícího metriky a zasílání do Zabbix proxy. Služba AWS CloudWatch nabízí další možné řešení v podobě Metric Streams integrující AWS Data Firehose, streamovací službu rozebranou níže. 

Každý Metric Stream může být konfigurován na určitou podmnožinu jmenných prostorů a metrik, jejichž statistiky posílá do dedikovaného Firehose delivery streamu v minutových intervalech\footnote{Statistiky jsou též počítány z metrik obdržených v témž minutovém okně}. Data generovaná z Metric Stream zahrnují všechny zaznamenané kombinace dimenzí metrik (a tedy i z nich vypočtených statistik). Pro Lambda funkce tedy například budou obsahovat požadované metriky napříč všemi funkcemi a verzemi (t.j. bez dimenze), metriky pro každou funkci jednotlivě napříč všemi verzemi a aliasy (dimenze názvu funkce) a metriky pro každou verzi a alias jednotlivě (dimenze názvu funkce a \uv{zdroje}), případně další. 

Výchozími statistikami posílanými z Metric Stream jsou průměr, minimum, maximum a počet hodnot metriky za dané minutové okno; další statistiky je možno dospecifikovat, ač s dodatečnými poplatky. Data je možné posílat ve formátech JSON, OpenTelemetry 1.0.0 nebo OpenTelemetry 0.7.0, pro další je nutné dále nakonfigurovat příslušný Firehose stream \cite{cloudwatch.docs.aws}.

Pro plné pochopení funkcionality Metric Stream je třeba seznámit se s AWS Data Firehose, napřed ale dokončeme analýzu AWS CloudWatch.

\subsubsection{Logy Lambda funkcí}
Kromě metrik CloudWatch ukládá také výpisy (logy) z různých zdrojů, včetně Lambda funkcí. Logy jsou textové záznamy o událostech, které se odehrály v monitorovaném systému, a mohou obsahovat informace o chybách, výkonu, nebo jiných událostech. Logy jsou ukládány do tzv. logovacích skupin (log groups), které jsou seskupeny pod logovacím tokem (log stream) \cite{cloudwatch.docs.aws}. U Lambda funkcí generuje AWS automatické logy ohledně režie invokace funkcí: například inicializace běhového prostředí, spuštění funkce a její konec, případně selhání (vyhození výjimky v kódu, timeout...), sumarizaci běhu obsahující dobu běhu, účtovanou dobu, využitou paměť atp. Běhová prostředí mají navíc předkonfigurovanou logovací knihovnu pro daný jazyk, která umožňuje snadné logování vlastních zpráv. Výpisy jsou opatřeny časovou značkou a identifikátorem požadavku (invokace/instance), vlastní výpisy navíc i logovací úrovní \cite{lambda.docs.aws}. Všimněme si, že z logů je možné odvozovat různé metriky, mnohé z nichž splývají s výše popsanými metrikami Lambda funkcí.

Logy je také možné posílat do ostatních služeb AWS: AWS Kinesis, AWS Data Firehose (stejně jako Metric Streams) nebo přímo do AWS Lambda funkce. Jelikož však logy nejsou předmětem této práce a k odvozování metrik je díky Metric Streams nepotřebujeme, nebudeme se jimi dále dopodrobna zabývat.

\subsection{AWS Data Firehose}
% co to je, transformace (neni specifikován formát události!)
Se službou AWS Data Firehose jsme se již setkali v kontextu Metric Stream. Služba slouží k posílání velkých dat (big data) od různých producentů, například právě Metric Stream, do jedné z několika možných cílových destinací. Firehose stream příchozí data sbírá (buffering) a posílá v dávkách záznamů (records, každý maximálně 1 000 KB). Sběr je možné ovlivnit dvěma vlastnostmi: doba sběru (buffer interval) a velikost dávky (buffer size). Data jsou sbírána po daný interval (v sekundách) nebo do naplnění dávky do specifikované velikosti (v MB), načež jsou poslána.

Producenti AWS Data Firehose se dělí na tři typy, jsou jimi Direct PUT, Amanzon Kinesis Data Streams a Amazon MSK. U posledních dvou se jedná o další streamovací služby AWS; Metric Streams spadá pod Direct PUT producenty, kteří posílají data do Firehose streamu přímo. Možných destinací je omezený počet, jejž z většiny tvoří služby AWS a služby třetích stran. Zabbix mezi službami není a tak bude potřeba prozkoumat jiné možnosti doručení dat z Metric Streams, jestliže se rozhodneme je využít. Poměrně flexibilními možnostmi jsou destinace AWS S3 bucket, pro niž AWS CloudWatch Metric Stream nabízí rychlou konfiguraci, a vlastní HTTP endpoint (server například běžící pod EC2), který je možné konfigurovat dle potřeb. 

HTTP endpoint nabízí více možností, jelikož se jedná o vlastní software schopný zpracovávat data přesně podle potřeb zákazníka, avšak je pro něj nutný udržovat dedikovaný server a správně implementovat API komunikující s Firehose streamem. Na druhou stranu destinace v podobě S3 bucketu nabízí v předešlé sekci zmíněné integrace s Lambda funkcemi, které mohou zpracovávat data z bucketu a posílat je dále do systému Zabbix. Bucket by v takovém případě sloužil pouze jako mezikrok pro přenos dat a výhodnější by bylo streamovat metriky přímo do Lambda funkce, avšak Firehose nenabízí Lambda funkci jako destinaci. Nicméně zpracovávání metrik z CloudWatch se zdá být výhodnější z Lambda funkce z důvodů nákladů na provoz, udržovatelnosti, škákovatelnosti (o niž se za nás bude starat AWS) a mezi dalšímí také \uv{sebe-monitorovatelnosti}: pokud impementace bude realizována v Lambda funkci, je možné samotnou monitorovací funkci monitorovat bez dalších nákladů.

Firehose nabízí další zajímavou možnost ve formě transformací vstupních dat. Podporované jsou transformace komprese a dekomprese, konverze formátu dat a obecná transformace pomocí vlastní Lambda funkce, na niž se v následujícím zaměřme. Při nastavené transformaci Lambda funkcí pro daný Firehose stream jsou vstupní data shraňována podobně jako při vstupu do streamu: do naplnění nastavené velikosti nebo vypršení časového intervalu. S první splněnou podmínkou jsou data poslána do transformační Lambda funkce, která je zpracuje a vrátí zpět do Firehose streamu. 

Transformační Lambda funkce je samozřejmě volána synchronně, jelikož Firehose čeká na zpracovaná data. Výstup transformační funkce je pak znovu shraňován jako při klasickém vstupu do Firehose streamu \cite{firehose.docs.aws} -- při využití transformace Lambda funkcí existují dvě rozdílná nastavení bufferingu, jedno pro vstup do Lambda funkce a druhé po výstupu z transformace před vstupem do streamu. Výstup Lamba funkce musí být ve specifickém formátu podle dokumentace AWS. Formát umožňuje označit výstupní (zpracované) záznamy jako zpracované, k zahození, nebo nezpracovatelné. Data k zahození nejsou poslána dále do streamu a nezpracovatelné způsobí chybu transformace.

Pro naše účely by bylo možné využít transformace Lambda funkcí pro změnu formátu vstupních dat na formát, kterému rozumí systém Zabbix (tělo HTTP požadavku volání Zabbix API). Možnosti zde ale nekončí. Jelikož se jedná o libovolně implementovanou Lambda funkci, můžeme ji zároveň využít pro poslání vstupních metrik do systému Zabbix, což řeší i předešlý problém, že Lamba funkci nelze nastavit jako destinaci Firehose streamu. 

Zde by mohla končit cesta dat na straně AWS, avšak je nutné destinaci specifikovat, ač pro ni nemusíme mít využití. Výchozí \uv{transformovaná} data nemají žadný význam, jelikož jsou z transformační funkce poslaná \uv{postranní cestou} do Zabbix a tak je možné všechny záznamy nechat prázdné a označit k zahození. Destinaci můžeme nastavit na S3 bucket, do nějž by se však nikdy žádná data zapsat neměla, neboť nastavení této destinace je nejsnazší a nejméně nákladné (není potřeba konfigurovat nevyužitou službu nebo HTTP endpoint). 

Všimněme si také, že taková transformační Lambda funkce zastává funkci návrhového vzoru adaptér, jelikož princip její činnosti spočívá v převodu vstupních dat z Metric Streamu do formátu požadovaného Zabbixem.

Nějaká data však do S3 bucketu zapisována být mohou, jelikož u této destinace AWS Data Firehose ukládá oznámení o chybách transformační Lambda funkce (timeout, výjimka při běhu...). Oznámení je soubor v JSON formátu nesoucí důvod chyby, počet pokusů volání transformace\footnote{Počet pokusů o nové volání je jedna z konfigurací transformace Lambda funkcí, spolu se zmíněnými buffering intervalem a velikostí} a kompletní vstup: metriky tak při chybě nejsou ztraceny. Maximální doba běhu transformační funkce je 5 minut, dá se však zkrátit v konfiguraci.

Analýza nám doteď odhalila způsob, jakým můžeme metriky z AWS CloudWatch Metric Stream dostat do systému Zabbix. V následujících kapitolách se zaměříme na analýzu systému Zabbix a jeho možností monitorování, předtím ale ještě stručně rozebereme službu AWS CloudFormation umožňující snadné nasazení komponent a správu infrastruktury v AWS.

\subsection{AWS CloudFormation}
AWS CloudFormation zprostředkovává přístup insfrastruktury jako kódu (IaC) v prostředí Amazon Web Services. Umožňuje definovat a nasadit celou infrastrukturu AWS pomocí šablon ve formátu JSON nebo YAML popisujících zdroje, jejich vlastnosti a vzájemné vztahy. CloudFormation poté zdroje nasadí a zajišťuje, že jsou vytvořeny v požadovaném stavu. Při změně šablony je možné CloudFormation použít k aktualizaci zdrojů, případně k jejich odstranění \cite{cloudformation.docs.aws}.

CloudFormation šablony se skládají ze tří hlavních částí: \emph{zdrojů} (resources), \emph{parametrů} (parameters) a \emph{výstupů} (outputs). Zdroje jsou jednotlivé komponenty infrastruktury, jako například EC2 instance, S3 buckety nebo Lambda funkce. Parametry jsou hodnoty, které mohou být při vytváření šablony zadány uživatelem. Výstupy jsou hodnoty, které jsou vytvořeny během vytváření zdrojů. V dalších šablonách je možné se na ně odkazovat \cite{cloudformation.docs.aws}.

Část vyvíjeného systému pro monitorování Lamba funkcí pomocí Zabbix může tak využívat CloudFormation šablony pro snadné nasazení potřebných zdrojů v AWS: doteď odhalený Metric stream, jeho Firehose stream a transformační Lambda funkci.

\subsubsection{AWS Serverless Application Model}

AWS Serverless Application Model (AWS SAM) je rozšíření CloudFormation umožňující efektivnější správu serverless aplikací v AWS. Šablony AWS SAM umožňují poskytovat zkrácený syntax definic serverless zdrojů jako napříkad Lamba funkce, DynamoDB tabulka nebo API Gateway. Také umožňují referovat na \uv{lokální zdroje}, soubory potřebné pro některé serverless komponenty, jako například adresář se zdrojovými kódy Lambda funkce. Bez AWS SAM není v CloudFormation možné kód složitější Lambda funkci poskytnout v šabloně a je třeba nejdříve všechny zdrojové soubory nahrát v ZIP archivu do S3 bucketu, na nějž se odkazuje šablona. Konzolový nástroj pro práci s AWS SAM (SAM CLI) se o takové případy dokáže postarat a projekt nasadit přímo z příkazové řádky. U Lambda funkcí také dokáže obstarat závislosti z typického manifestačního souboru pro daný jazyk funkce -- například pro python stačí poskytnout soubor \texttt{requirements.txt}, pro Node.js \texttt{package.json} atp.

Kromě usnadnění nasazování aplikací nástroj SAM CLI poskytuje mnohé další výhodné funkcionality. Patří mezi ně například lokální či vzdálené spuštění funkce, testování nebo generování vzorových událostí (vstupních dat funkce) generovaných různými AWS službami.
