\section{Analýza dostupných služeb AWS}
Amazon Web Services (AWS) je jedním ze současným největších poskytovatelů cloudových služeb na trhu. Nabízí širokou škálu služeb, které umožňují vytváření a provozování škálovatelných a spolehlivých aplikací. Z tohoto obrovského množství služeb musíme vybrat relevantní podmnožinu pro daný problém.

\subsection{AWS Elastic Compute Cloud}
Elastic Compute Cloud, zkráceně EC2, je základní služba AWS, která poskytuje škálovatelné výpočetní kapacity v cloudu ve formě virtuálních serverů neboli instancí. Každá instance slouží jako samostatný virtuální stroj, který si uživatel spravuje dle svých potřeb. EC2 podporuje různé operačních systémy, včetně různých distribucí Linuxu a Windows Serveru. Uživatelé mohou také vytvářet vlastní Amazon Machine Images (AMI), která obsahují předkonfigurované prostředí pro specifické aplikace. Je zřejmé, že EC2 nespadá pod serverless computing, neboť uživatel je zodpovědný za správu instancí.

Jelikož se jedná o centrální službu, můžeme v AWS najít mnoho dalších způsobů konfigurace EC2 instancí i služeb s nimi spojených, jako například automatické škálování, load balancing, nebo služby pro správu virtuální sítě.

Pro účely monitorovacího systému je možné na EC2 instancích provozovat vlastní Zabbix server a proxy, ale také případně provozovat software sloužící jako prostředník mezi AWS a Zabbix proxy.

\subsection{AWS Lambda}
AWS Lambda funkcím, jakožto hlavní službě této práce, věnujme v této sekci intenzivní pozornost. Jedná se implementaci FaaS paradigmatu v AWS s podporou pro mnoho vývojářských prostředí (různé programovací jazyky a Docker kontejnery). Programátor poskytne kód funkce\footnote{Reálně se nemusí jednat o jednu proceduru programovacího jazyka, může být poskytnut malý program} se vstupním bodem implementujícím rozhraní specifikované pro dané prostředí (hlavička vstupní procedury) a AWS se postará o její nasazení, běh a škálování. Lambda funkce jsou spouštěny na základě uživatelem specifikovaných událostí, například voláním AWS API pomocí nástroje z příkazové řádky, událostí generovanou jinou AWS službou (S3, Firehose, SQS...), nebo na základě časovače \cite{lambda.docs.aws}. Uživateli je účtováno pouze za čas, po který je funkce spuštěna, za využití paměti a za počet požadavků (spuštění funkce) \cite{lambda.pricing.aws}.

\subsubsection{Vývoj Lambda funkcí}
Vývoj Lambda funkcí je možný v několika programovacích jazycích, mezi které patří Python, Node.js, Java, Go, Ruby, C\# a PowerShell. Vstupní bod funkce, neboli \uv{handler}, musí implementovat požadované rozhraní, které se konkrétně mění pro každý jazyk dle dokumentace (např. funkce pro Python, Node.js nebo třída implementující rozhraní v jazyce Java), avšak všechny mají společný tvar -- přijímají dva argumenty, událost (event) a kontext (context), a vrací výsledek typicky ve formátu JSON. Událost obsahuje vstupní data funkce, poskytnutá volajícím, tedy např. uživatelem invokujícím Lambda funkci z příkazové řádky nebo AWS službou (formát pak odpovídá specifikaci dané služby\footnote{U některých služeb však formát události není v dokumentaci uveden... Viz dále.}). Kontext je zpravidla objekt obsahující informace o běhu funkce, jako například velikost paměti, čas spuštění, nebo identifikátor požadavku (volání) \cite{lambda.docs.aws}.

Kód funkce je možné nahrát do AWS více způsoby: při vytváření funkce v grafickém rozhraní AWS (AWS Management Console), pomocí nástroje SAM, krátké funkce přímo v šabloně CloudFormation atp. Program se uloží do komprimovaného archivu ve formátu ZIP do automaticky vytvořeného S3 bucketu. Složitější funkce, které vyžadují větší množství souborů a závislostí, je třeba nahrát do S3 bucketu ručně a poté vytvořit funkci s odkazem na tento bucket, anebo je možné využít zmíněného nástroje SAM, jehož cílem je zjednodušit nasazení serverless aplikací v AWS \cite{sam.docs.aws, lambda.docs.aws}. 

Závislosti, soubory anebo vlastní výpočetní prostředí sdílené více funkcemi je možné poskytnout jako tzv. vrstvu (layer) ve vlastním ZIP archivu, na niž se Lambda funkce odkazují. Některé závislosti jsou dostupné přímo v AWS Lambda prostředí, zejména knihovny pro práci s AWS službami (AWS SDK). Mimo vrstvy je také k funkcím možno připojit rozšíření (extension), dodané také jako ZIP archiv. Rozšíření mohou být externí, běžící jako nezávislý proces uvnitř výpočetního prostředí, anebo interní jako vlákno procesu řídícího Lambda funkci. AWS Lambda poskytuje některá již hotová rozšíření, zejména od partnerů třetích stran, mnoho z nichž se orientují právě na monitoring, observability a bezpečnost. Zabbix se však mezi partnery nevyskytuje \cite{lambda.docs.aws}.

Kromě archivu umožňuje AWS poskytnout funkci jako Docker image, ač je v takovém případě nutno poskytnout program implementující REST API rozhraní zprostředkující komunikaci mezi kontejnerem a službou AWS Lambda\footnote{vývojáři AWS však připravili několik Docker image, na nichž je možno stavět Lambda funkce, které takový program obsahují}. U Docker image navíc nejsou podporovány vrstvy \cite{lambda.docs.aws}.

\subsubsection{Invokace Lambda funkcí}
Dokumentace AWS Lambda specifikuje různé způsoby, jak může být funkce spuštěna. Základní rozdělení definuje synchronní a asynchronní volání, přičemž synchronní volání je \uv{blokující} a vrací výsledek volání, zatímco asynchronní volání vloží vstup do fronty událostí v AWS a na výstup nečeká, zahazuje jej. Oba typy volání je možné provést pomocí AWS Management Console, AWS CLI, SDK nebo API. Maximální velikost vstupních dat je omezena na 6 MB \cite{lambda.docs.aws}.

Lambda funkce je možné integrovat s dalšími službami AWS, které invokují funkce automaticky. Integraci uživatel realizuje při konfiguraci služby, kterou plánuje využívat. Různé služby mouhou funkce volat synchronně nebo asynchronně dle dokumentace. V tomto případě invokací však dochází k dalšímu dělení na \uv{triggered} a \uv{event source mapping} invokace. Některé služby volají Lambda funkce ze své strany pomocí triggerů, poskytujíce vstupní data samy, kdežto zejména streamovací služby (např. Kinesis, DynamoDB) využívají event source mapping, zdroj na straně AWS Lambda, držící tzv. \uv{event poller} komponenty, které získávají dávky událostí (vstupních dat) ze zdrojové služby a posílají je do cílové Lambda funkce. Cílem event source mapping je zpracování velkého množství dat v jednom volání funkce a v důsledku zvýšení propustnosti oproti volání Lambda funkce pro každou položku ve streamu. Velikost dávky je dále možné konfigurovat podle počtu událostí v dávce a doby trvání sběru událostí do jedné dávky a také podléhá omezení na 6 MB \cite{lambda.docs.aws}.

\subsubsection{Škálování a konkurentnost}
AWS Lambda automaticky (horizontálně) škáluje volání funkcí podle počtu požadavků, nad nimiž je funkce volána. Každá funkce běží v izolovaném prostředí vyhrazeném pouze pro ni. Před prvním voláním je ze strany AWS nutné prostředí připravit (\uv{init} fáze) a až následně může funkce zpracovávat požadavky. Prostředí je udržováno po určitou dobu po posledním volání, aby bylo možné funkci spustit rychleji nad budoucími invokacemi. Při vhodném časování doby běhu funkce a příchody požadavků je tedy možné, že veškeré požadavky budou zpracovány v jednom prostředí. Běžně ale nastávají situace, kdy do funkce přichází více požadavků, než je jedna instance schopna odbavit a je třeba funkci spouštět konkurentně.

Konkurentnost (Concurrency) je v AWS dokumentaci chápána jednak jako veličina a jednak jako počet prostředí vyhrazených pro uživatelovy Lambda funkce. Standardní horní limit konkurentnosti je ze strany AWS nastaven na 1000, což prakticky také znamená, že v jeden moment je umožněn běh maximálně 1000 funkcí (v účtu na region). V základním nastavení je tato konkurentnost sdílena mezi všechny funkce v účtu, ale je možné ji nastavit i pro jednotlivé funkce a to dvojím způsobem. Každá funkce může mít nastaven počet \uv{vyhrazené} (reserved) konkurentnosti a \uv{nasazené} (provisioned) konkurentnosti. Vyhrazená konkurentnost udává počet volných a vyhrazených prostředí pro danou funkci, omezujíc tak sdílenou konkurentnost, zároveň ale tento počet shora limituje: funkce nemůže běžet ve více prostředích, než je specifikováno tímto parametrem, a nemůže tedy využívat zbývající sdílenou konkurentnost.

Nasazená konkurentnost je podobná vyhrazené s tím rozdílem, že udává počet \emph{již připravených} prostředí. Při zvýšení (v mezích nasazené konkurentnosti) skutečné konrkurentnosti funkce tak není třeba nové prostředí inicializovat, jelikož již připravené je. U Lambda funkcí je možné nastavit obě konkurentnosti nezávisle, avšak specifikace obou zároveň má smysl pouze v případě, kdy vyhrazená je vyšší než nasazená.

Jestliže funkce vyčerpá svou konkurentnost nebo je vyčerpána sdílená konkurntnost nenastavenými funkcemi, nové požadavky mohou být odmítnuty a zahozeny. Tento jev se nazývá throttling. Navíc AWS nedovoluje omezit sdílenou konkurentnost pod hodnotu 100.

Hodnotu očekávané konkurentnosi $C_f$ funkce $f$ je možné zjistit ze vzathu

$$C_f = \pi_f \cdot \delta_f, $$

kde $\pi_f$ je očekávaný počet požadavků za sekundu a $\delta_f$ je očekávaná doba trvání funkce v sekundách. 

\subsubsection{Verzování}
Lambda umožňuje pro potřeby kontinuálního vývoje funkce verzovat. Funkce je možné vyvíjet/upravovat a testovat ještě před zveřejněním a následně publikovat novou verzi, která je dostupná pro volání. Zveřejněné verze obdrží unikátní monotónně se zvyšující identifikátor a nejde je dále měnit. Konkrétní verze mohou být označeny aliasy sloužícími k přesměrování volání. Aliasy je možné přesměrovat pro plynulý přechod mezi verzemi funkce. AWS navíc umožňujě definovat \emph{vážený alias}, který umožňuje rozdělit provoz mezi dvěmi verzemi podle zadaného poměru, jako podporu \emph{canary deployment} pro účely CI/CD \cite{lambda.docs.aws}.

\subsection{AWS Simple Storage Service}
Další významnou službou AWS je Simple Storage Service, zkráceně S3. Jedná se o službu pro ukládání a správu dat v cloudu. S3 je vhodné pro ukládání velkého množství dat, jako jsou například statické webové stránky, zálohování, nebo multimediální soubory. S3 nabízí různé třídy úložišť podle předpokládané frekvence přístupu a širokou škálu funkcí, jako je šifrování, správa přístupových práv nebo verze souborů. Mnoho dalších služeb AWS integruje S3 pro své účely. Základní přístup k S3 je přes REST API, ale AWS poskytuje i SDK pro mnoho programovacích jazyků. Další možností je využití tzv. \emph{přístupových bodů} (access points) pro jednodušší a konfigurovatelný přístup k datům \cite{s3.docs.aws}.

Data jsou v S3 ukládána jako \emph{objekty}, soubory s metadaty popisujícími vlastnosti souboru, do kontejnerů zvaných \emph{buckety}. Buckety se dělí do dvou druhů: General purpose buckets (pro obecné účely) a Directory buckets (adresářové), kde první druh ukládá objekty s unikátním názvem (klíčem) v ploché struktuře, kdežto druhý spravuje objekty hierarchicky v adresářové strukutře. Objekt je pak identifikován bucketem, unikátním klíčem (vč. cesty u adresářových bucketů) a případně verzí.

Simple Storage Service využívá silný konzistenční model \todo{teorie ke konzistenčním modelům} \emph{read-after-write}; všechny čtecí operace vracejí hodnotu poslední dokončené zapisovací operace, u konkurentních zápisů však není jisté, který z nich \uv{vyhraje}. AWS S3 používá sémantiku \emph{last-writer-wins}, tedy poslední zápis má přednost, avšak kvůli nespolehlivosti sítě není možné určit, který konkurentní zápis dorazí jako poslední \cite{s3.docs.aws}.

AWS S3 je možné integrovat s AWS Lambda funkcemi a to několika způsoby. Jedním je využití S3 Object Lambda, umožnující transformovat data vrácená čtecími požadavky na objekty S3 pomocí specializovaných přístupových bodů. Požadavek na objekt je přesměrován na standardní přístupový bod, jehož výstup je zpracován poskytnutou Lambda funkcí a následně zaslán klientovi \cite{s3.docs.aws}. Další možností je zasílání notifikací o změnách S3 objektů (např. vytvoření/odstranění). Po dokončení změny objektu služba S3 asynchronně invokuje (triggered invokace) zaregistrované Lambda funkce se vstupem popisujícím událost \cite{lambda.docs.aws}. Funkce pak může na změnu libovolně reagovat.

\subsection{AWS CloudWatch}
% metriky, logy, granularita, alarmy, metric streams + FireHose
Další analyzovanou službou nechť je AWS CloudWatch. Jedná se o službu pro monitorování a logování v AWS, která umožňuje sledovat metriky a výpisy (logy) z různých zdrojů, jako jsou například EC2 instance, Lambda funkce, nebo S3 buckety. Metriky jsou číselné hodnoty, které měří výkon služeb AWS a zdrojů, které jsou s nimi spojeny. Metriky jsou agregovány do tzv. \uv{statistik}, které mohou být zobrazeny v grafu na výchozí nebo vlastní \uv{nástěnce} (dashboard) nebo použity pro vytváření alarmů, konfigurovatelných notifikací zasílaných při dosažení určité hodnoty zvolené statistiky \cite{cloudwatch.docs.aws}. Je zřejmé, že CloudWatch bude stěžejní službou pro vyvíjený systém, neboť poskytuje veškeré potřebné informace pro monitorování Lambda funkcí. Hlavním cílem práce je dopravit tyto informace (resp. jejich konfigurovatelnou podmnožinu) do interního monitorovacího systému Zabbix.

Jelikož naším hlavním zájmem jsou Lambda funkce, budeme se v této sekci dále zaměřovat pouze na možnosti monitorování těchto funkcí v rámci CloudWatch.

\subsubsection{Metriky Lambda funkcí}
Metrika je z pohledu CloudWatch pojmenovaná časově seřazená množina hodnot nějaké proměnné, například využití CPU (u EC2 instancí) nebo doba výpočtu Lambda funkce. CloudWatch dělí metriky do tzv. jmenných prostorů (Namespaces), které slouží k organizaci metrik, zajištění jednoznačnosti jejich názvů a izolaci. Každá monitorovatelná AWS služba má svůj vyhrazený Namespace, pro Lambda funkce je to \texttt{AWS/Lambda}, a další jmenné prostory může definovat uživatel. 

Kromě jmenného prostoru a názvu jsou metriky definovány ještě \emph{dimezemi}. Dimenze je dvojice název-hodnota přidávající další identitu dané metrice. Názvy dimenzí jsou kategorie, do nichž může metrika patřit, například jméno Lambda funkce, verze, nebo region, ve kterém je funkce spuštěna. Hodnoty dimenzí jsou konkrétní instance těchto kategorií, které od sebe oddělují metriky. Metrika může mít až 30 dimenzí (nebo žádnou). Dimenze se dají libovolně kombinovat a hodnota metriky se uloží pouze pro danou kombinaci dimenzí. Monitorovatelné služby definují vlastní dimenze a narozdíl od uživatelsky definovaných dimenzí je služba AWS CloudWatch schopna agregovat hodnoty z vynechaných dimenzí \cite{cloudwatch.docs.aws}. 

CloudWatch všechny metriky agreguje do statistik, které mohou být zobrazeny v grafu nebo použity pro vytváření alarmů, z hodnot metrik za určitý časový interval. Poskytované statistiky jsou například průměr, maximum a minimum, suma, počet hodnot nebo některé percentily \cite{cloudwatch.docs.aws}.

Služba AWS Lambda zaznamenává mnoho metrik a dělí je na několik druhů. Některé z nich jsou \cite{lambda.docs.aws}:

\begin{itemize}
    \item metriky invokací -- příznakové binární metriky, pro něž má smysl pouze statistika součtu
    \begin{itemize}
        \item \texttt{Invocations} -- počet invokací funkce
        \item \texttt{Errors} -- počet selhaných invokací
        \item \texttt{DeadLetterErrors} -- počet selhaných pokusů o zápis do Dead Letter Queue asynchronními invokacemi
        \item \texttt{Throttles} -- počet odmítnutých invokací kvůli nedostatku konkurentnosti
    \end{itemize}
    \item metriky výkonu
    \begin{itemize}
        \item \texttt{Duration} -- doba trvání funkce, podporuje kvantilové statistiky
        \item \texttt{IteratorAge} -- věk nejstaršího zpracovávaného záznamu v události vzniklé při event source mapping pro Kinesis stream
    \end{itemize}
    \item metriky konkurentnosi
    \begin{itemize}
        \item \texttt{ConcurrentExecutions} -- počet současně běžících instancí funkce
        \item \texttt{UnreservedConcurrentExecutions} -- počet současně běžících instancí funkce, které není vyhrazena konkurentnost
        \item \texttt{ClaimedAccountConcurency} -- počet spuštěných prostředí (využitá konkurentnost)
    \end{itemize}
\end{itemize}

Z výpisu je zřejmé, že ne všechny metriky se týkají přímo Lambda funkcí, některé monitorují jiné činnosti služby AWS Lambda. Například metrika \texttt{ClaimedAccountConcurency} znázorňuje využitou konkurentnost v účtu a regionu skrz všechny funkce. Dle zadání práce je třeba umožnit monitorování pouze metrik přímo souvisejících s funkcemi, dále tedy pracujme pouze v jejich kontextu. 

Všechny takové metriky definují dimenze pro název funkce, \uv{zdroj} (resource), pod niž spadají verze a aliasy funkce, a některé další. Dokumentace tuto skutečnost dopodrobna nerozvíjí a pouze se letmo o dimenzích metrik pro AWS Lambda zmiňuje, a tak byl tento poznatek zjištěn experimentálně\footnote{Během vývoje ve zkušebním stavu, kdy byl zkoumán formát požadavků do transformační Lambda funkce z Data Firehose se zdrojem v Metric streamu, viz dále.}. Vyvíjený systém má dle požadavků zákazníka monitorovat metriky pro jednotlivé funkce bez odlišování verzí, což prakticky znamená, že bude třeba exportovat metriky pouze s dimenzí názvu funkce. AWS Lambda do těchto metrik automaticky agreguje i hodnoty pro všechny verze a aliasy funkce s daným názvem, jak bylo poznamenáno výše.

\subsubsection{Metric Stream}
V této fázi analýzy již známe dostatek o poskytovaných metrikách Lambda funkcí, dále bude potřeba najít způsob, jak je dostat do externího systému Zabbix. Možností se nabízí spousta, například periodické volání AWS API v procesu nové EC2 instance nebo ve vyhrazené Lambda funkci, vývoj exportovací procedury/knihovny, její připojení k monitorovaným funkcím v nové vrstvě a následné volání z kódu nebo připojení vlastního rozšíření Lambda funkce sbírajícího metriky a zasílání do Zabbix proxy. Služba AWS CloudWatch nabízí další možné řešení v podobě Metric Streams integrující AWS Data Firehose, streamovací službu rozebranou níže. 

Každý Metric Stream může být konfigurován na určitou podmnožinu jmenných prostorů a metrik, jejichž statistiky posílá do dedikovaného Firehose delivery streamu v minutových intervalech\footnote{Statistiky jsou též počítány z metrik obdržených v témž minutovém okně}. Data generovaná z Metric Stream zahrnují všechny zaznamenané kombinace dimenzí metrik (a tedy i z nich vypočtených statistik). Pro Lambda funkce tedy například budou obsahovat požadované metriky napříč všemi funkcemi a verzemi (t.j. bez dimenze), metriky pro každou funkci jednotlivě napříč všemi verzemi a aliasy (dimenze názvu funkce) a metriky pro každou verzi a alias jednotlivě (dimenze názvu funkce a \uv{zdroje}), případně další. 

Výchozími statistikami posílanými z Metric Stream jsou průměr, minimum, maximum a počet hodnot metriky za dané minutové okno; další statistiky je možno dospecifikovat, ač s dodatečnými poplatky. Data je možné posílat ve formátech JSON, OpenTelemetry 1.0.0 nebo OpenTelemetry 0.7.0, pro další je nutné dále nakonfigurovat příslušný Firehose stream \cite{cloudwatch.docs.aws}.

Pro plné pochopení funkcionality Metric Stream je třeba seznámit se s AWS Data Firehose, napřed ale dokončeme analýzu AWS CloudWatch.

\subsubsection{Logy Lambda funkcí}
Kromě metrik CloudWatch ukládá také výpisy (logy) z různých zdrojů, včetně Lambda funkcí. Logy jsou textové záznamy o událostech, které se odehrály v monitorovaném systému, a mohou obsahovat informace o chybách, výkonu, nebo jiných událostech. Logy jsou ukládány do tzv. logovacích skupin (log groups), které jsou seskupeny pod logovacím tokem (log stream) \cite{cloudwatch.docs.aws}. U Lambda funkcí generuje AWS automatické logy ohledně režie invokace funkcí: například inicializace běhového prostředí, spuštění funkce a její konec, případně selhání (vyhození výjimky v kódu, timeout...), sumarizaci běhu obsahující dobu běhu, účtovanou dobu, využitou paměť atp. Běhová prostředí mají navíc předkonfigurovanou logovací knihovnu pro daný jazyk, která umožňuje snadné logování vlastních zpráv. Výpisy jsou opatřeny časovou značkou a identifikátorem požadavku (invokace/instance), vlastní výpisy navíc i logovací úrovní \cite{lambda.docs.aws}. Všimněme si, že z logů je možné odvozovat různé metriky, mnohé z nichž splývají s výše popsanými metrikami Lambda funkcí.

Logy je také možné posílat do ostatních služeb AWS: AWS Kinesis, AWS Data Firehose (stejně jako Metric Streams) nebo přímo do AWS Lambda funkce. Jelikož však logy nejsou předmětem této práce a k odvozování metrik je díky Metric Streams nepotřebujeme, nebudeme se jimi dále dopodrobna zabývat.

\subsection{AWS Data Firehose}
% co to je, transformace (neni specifikován formát události!)
Se službou AWS Data Firehose jsme se již setkali v kontextu Metric Stream. Služba slouží k posílání velkých dat (big data) od různých producentů, například právě Metric Stream, do jedné z několika možných cílových destinací. Firehose stream příchozí data sbírá (buffering) a posílá v dávkách záznamů (records, každý maximálně 1 000 KB). Sběr je možné ovlivnit dvěma vlastnostmi: doba sběru (buffer interval) a velikost dávky (buffer size). Data jsou sbírána po daný interval (v sekundách) nebo do naplnění dávky do specifikované velikosti (v MB), načež jsou poslána.

Producenti AWS Data Firehose se dělí na tři typy, jsou jimi Direct PUT, Amanzon Kinesis Data Streams a Amazon MSK. U posledních dvou se jedná o další streamovací služby AWS; Metric Streams spadá pod Direct PUT producenty, kteří posílají data do Firehose streamu přímo. Možných destinací je omezený počet, jejž z většiny tvoří služby AWS a služby třetích stran. Zabbix mezi službami není a tak bude potřeba prozkoumat jiné možnosti doručení dat z Metric Streams, jestliže se rozhodneme je využít. Poměrně flexibilními možnostmi jsou destinace AWS S3 bucket, pro niž AWS CloudWatch Metric Stream nabízí rychlou konfiguraci, a vlastní HTTP endpoint (server například běžící pod EC2), který je možné konfigurovat dle potřeb. 

HTTP endpoint nabízí více možností, jelikož se jedná o vlastní software schopný zpracovávat data přesně podle potřeb zákazníka, avšak je pro něj nutný udržovat dedikovaný server a správně implementovat API komunikující s Firehose streamem. Na druhou stranu destinace v podobě S3 bucketu nabízí v předešlé sekci zmíněné integrace s Lambda funkcemi, které mohou zpracovávat data z bucketu a posílat je dále do systému Zabbix. Bucket by v takovém případě sloužil pouze jako mezikrok pro přenos dat a výhodnější by bylo streamovat metriky přímo do Lambda funkce, avšak Firehose nenabízí Lambda funkci jako destinaci. Nicméně zpracovávání metrik z CloudWatch se zdá být výhodnější z Lambda funkce z důvodů nákladů na provoz, udržovatelnosti, škákovatelnosti (o niž se za nás bude starat AWS) a mezi dalšímí také \uv{sebe-monitorovatelnosti}: pokud impementace bude realizována v Lambda funkci, je možné samotnou monitorovací funkci monitorovat bez dalších nákladů.

Firehose nabízí další zajímavou možnost ve formě transformací vstupních dat. Podporované jsou transformace komprese a dekomprese, konverze formátu dat a obecná transformace pomocí vlastní Lambda funkce, na niž se v následujícím zaměřme. Při nastavené transformaci Lambda funkcí pro daný Firehose stream jsou vstupní data shraňována podobně jako při vstupu do streamu: do naplnění nastavené velikosti nebo vypršení časového intervalu. S první splněnou podmínkou jsou data poslána do transformační Lambda funkce, která je zpracuje a vrátí zpět do Firehose streamu. 

Transformační Lambda funkce je samozřejmě volána synchronně, jelikož Firehose čeká na zpracovaná data. Výstup transformační funkce je pak znovu shraňován jako při klasickém vstupu do Firehose streamu \cite{firehose.docs.aws} -- při využití transformace Lambda funkcí existují dvě rozdílná nastavení bufferingu, jedno pro vstup do Lambda funkce a druhé po výstupu z transformace před vstupem do streamu. Výstup Lamba funkce musí být ve specifickém formátu podle dokumentace AWS. Formát umožňuje označit výstupní (zpracované) záznamy jako zpracované, k zahození, nebo nezpracovatelné. Data k zahození nejsou poslána dále do streamu a nezpracovatelné způsobí chybu transformace.

Pro naše účely by bylo možné využít transformace Lambda funkcí pro změnu formátu vstupních dat na formát, kterému rozumí systém Zabbix (tělo HTTP požadavku volání Zabbix API). Možnosti zde ale nekončí. Jelikož se jedná o libovolně implementovanou Lambda funkci, můžeme ji zároveň využít pro poslání vstupních metrik do systému Zabbix, což řeší i předešlý problém, že Lamba funkci nelze nastavit jako destinaci Firehose streamu. 

Zde by mohla končit cesta dat na straně AWS, avšak je nutné destinaci specifikovat, ač pro ni nemusíme mít využití. Výchozí \uv{transformovaná} data nemají žadný význam, jelikož jsou z transformační funkce poslaná \uv{postranní cestou} do Zabbix a tak je možné všechny záznamy nechat prázdné a označit k zahození. Destinaci můžeme nastavit na S3 bucket, do nějž by se však nikdy žádná data zapsat neměla, neboť nastavení této destinace je nejsnazší a nejméně nákladné (není potřeba konfigurovat nevyužitou službu nebo HTTP endpoint). 

Všimněme si také, že taková transformační Lambda funkce zastává funkci návrhového vzoru adaptér, jelikož princip její činnosti spočívá v převodu vstupních dat z Metric Streamu do formátu požadovaného Zabbixem.

Nějaká data však do S3 bucketu zapisována být mohou, jelikož u této destinace AWS Data Firehose ukládá oznámení o chybách transformační Lambda funkce (timeout, výjimka při běhu...). Oznámení je soubor v JSON formátu nesoucí důvod chyby, počet pokusů volání transformace\footnote{Počet pokusů o nové volání je jedna z konfigurací transformace Lambda funkcí, spolu se zmíněnými buffering intervalem a velikostí} a kompletní vstup: metriky tak při chybě nejsou ztraceny. Maximální doba běhu transformační funkce je 5 minut, dá se však zkrátit v konfiguraci.

Analýza nám doteď odhalila způsob, jakým můžeme metriky z AWS CloudWatch Metric Stream dostat do systému Zabbix. V následujících kapitolách se zaměříme na analýzu systému Zabbix a jeho možností monitorování, předtím ale ještě stručně rozebereme službu AWS CloudFormation umožňující snadné nasazení komponent a správu infrastruktury v AWS.

\subsection{AWS CloudFormation}
AWS CloudFormation zprostředkovává přístup insfrastruktury jako kódu (IaC) v prostředí Amazon Web Services. Umožňuje definovat a nasadit celou infrastrukturu AWS pomocí šablon ve formátu JSON nebo YAML popisujících zdroje, jejich vlastnosti a vzájemné vztahy. CloudFormation poté zdroje nasadí a zajišťuje, že jsou vytvořeny v požadovaném stavu. Při změně šablony je možné CloudFormation použít k aktualizaci zdrojů, případně k jejich odstranění \cite{cloudformation.docs.aws}.

CloudFormation šablony se skládají ze tří hlavních částí: \emph{zdrojů} (resources), \emph{parametrů} (parameters) a \emph{výstupů} (outputs). Zdroje jsou jednotlivé komponenty infrastruktury, jako například EC2 instance, S3 buckety nebo Lambda funkce. Parametry jsou hodnoty, které mohou být při vytváření šablony zadány uživatelem. Výstupy jsou hodnoty, které jsou vytvořeny během vytváření zdrojů. V dalších šablonách je možné se na ně odkazovat \cite{cloudformation.docs.aws}.

Část vyvíjeného systému pro monitorování Lamba funkcí pomocí Zabbix může tak využívat CloudFormation šablony pro snadné nasazení potřebných zdrojů v AWS: doteď odhalený Metric stream, jeho Firehose stream a transformační Lambda funkci.

\subsubsection{AWS Serverless Application Model}

AWS Serverless Application Model (AWS SAM) je rozšíření CloudFormation umožňující efektivnější správu serverless aplikací v AWS. Šablony AWS SAM umožňují poskytovat zkrácený syntax definic serverless zdrojů jako napříkad Lamba funkce, DynamoDB tabulka nebo API Gateway. Také umožňují referovat na \uv{lokální zdroje}, soubory potřebné pro některé serverless komponenty, jako například adresář se zdrojovými kódy Lambda funkce. Bez AWS SAM není v CloudFormation možné kód složitější Lambda funkci poskytnout v šabloně a je třeba nejdříve všechny zdrojové soubory nahrát v ZIP archivu do S3 bucketu, na nějž se odkazuje šablona. Konzolový nástroj pro práci s AWS SAM (SAM CLI) se o takové případy dokáže postarat a projekt nasadit přímo z příkazové řádky. U Lambda funkcí také dokáže obstarat závislosti z typického manifestačního souboru pro daný jazyk funkce -- například pro python stačí poskytnout soubor \texttt{requirements.txt}, pro Node.js \texttt{package.json} atp.

Kromě usnadnění nasazování aplikací nástroj SAM CLI poskytuje mnohé další výhodné funkcionality. Patří mezi ně například lokální či vzdálené spuštění funkce, testování nebo generování vzorových událostí (vstupních dat funkce) generovaných různými AWS službami.

\section{Systém Zabbix}
Zabbix je open-source monitorovací systém umožňující sledovat stav různých komponent infrastruktury. Je schopen monitorovat širokou škálu služeb a zdrojů, jako jsou například servery, databáze, síťová zařízení, cloudové služby nebo vlastní aplikace. Zabbix implementuje push i pull modely monitorování \cite{zabbix.docs}.

Pro pokračování analýzy možných řešení pro monitorování Lambda funkcí v Zabbixu je třeba se seznámit s jeho architekturou, komponentami a funkcemi k odhalení možnosti doručit metriky z výše popsané transformační Lambda funkce do instance Zabbix serveru. Na přání zákazníka se budeme věnovat již nepodporované verzi Zabbix 5.4.

\subsection{Komponenty Zabbix}
Systém sestává z několika komponent, jimiž jsou Zabbix server, frontend, agent a volitelně proxy. Server je hlavní komponentou systému, která ukládá a zpracovává metriky. Zabbix agent je software nainstalovaný na monitorovaných zařízeních, který sbírá data a posílá je na server, případně na proxy. Frontend je webové rozhraní pro uživatele, které umožňuje zobrazovat metriky, vytvářet grafy, alarmy a další. Proxy je volitelná komponenta distribující zátěž od serveru \cite{zabbix.docs}.

Proxy a agenti mohou být konfigurováni jako aktivní nebo pasivní, nastavení odpovídající modelům push a pull. V aktivním modelu agenti a proxy pravidelně posílají data na server, zatímco v pasivním modelu server žádá o data agenty a proxy. Aktivní model je výchozí \cite{zabbix.docs}.

Z komponent by mohl sloužit vyvíjenému systému Zabbix agent, jelikož se stará o sběr a posílání metrik do centrální komponenty, serveru. V našem případě je však provoz specificky nakonfigurovaného agenta problematický kvůli serverless schámatu transformační Lambda funkce\footnote{Nespravujeme server, na němž funkce běží, a nemůžeme tak agenta předinstalovat.}. Nabízí se teoretická možnost poskytnout agenta jako externí rozšíření Lambda funkce, přičemž by byla potřeba zajistit komunikaci mezi agentem a kódem funkce, nebo možnost implementovat protokol Zabbix agenta v transformační Lambda funkci, aby se serveru (nebo proxy) tvářila sama jako \emph{aktivní} agent. V další sekci však zjistíme, že Zabbix nabízí vhodnější možnosti bez nutnosti instalace agenta.

\subsection{Pojmy, funkce}
% pojmy -- host, item, severity, trigger, discovery, makra, trapper itemy
% funkce -- LLD + keep period, API, Zabbix sender
V rámci systému Zabbix je definováno několik typů záznamů nebo kategorií, s nimiž je operováno. Na nejnižší úrovni se vyskytují \uv{datové elementy}\footnote{Pro český překad některých anglických pojmů byl využit oficiální překlad dokumentace Zabbix v ruském jazyce.} (\emph{item}), které odpovídají metrikám z AWS CloudWatch\footnote{i když technicky jejich hodnoty budou nabývat hodnot statistik z AWS CloudWatch, jelikož neagregované metriky nejsou poskytovány, viz výše}; jedná se o časově seřazené hodnoty nějaké veličiny identifikované \uv{klíčem} (\emph{item key}). Itemy jsou přiřazeny k \uv{síťovým uzlům} (\emph{host}), které abstrahují původce metrik, například server, směrovač (router) nebo Lambda funkce\footnote{v našem případě ve výsledném systému technicky však spíše AWS CloudWatch nebo AWS Lambda jako celá služba}. Host může mít libovolné množství itemů. Síťové elementy jsou dále seskupeny do \uv{skupin síťových elementů} (\emph{host group}), které usnadňují správu a organizaci hostů.

Dále rozeberme tyto a další pojmy a funkce Zabbixu podrobně.

\subsection{Makra}
Zabbix umožňuje definovat \uv{makra}, pojmenované uživatelské hodnoty, která mohou být použity na různých místech konfigurace systému. Makra se dělí na \uv{vnitřní}, \uv{uživatelská} a \uv{uživatelská s kontextem}. Vnitřní makra jsou předdefinovaná a jejich hodnota může záviset, na kterém z pro dané makro podporovaných místech je použito -- například makro pro poslední hodnotu itemu. Uživatelská makra jsou definována uživatelem na jedné z několika úrovní, jimiž jsou globální úroveň, úroveň specifického hosta a úroveň šablony\footnote{Šablony budou předmětem pozdější sekce}.

Uživatelská makra s kontextem mají stejné využití jako makra bez kontextu, ale umožňují \uv{zastiňovat} výchozí hodnotu makra. V definici makra je v názvu specifikován kontext jako konkrétní textový řetězec nebo jako regulární výraz. Při použití makra je také možné specifikovat kontext, v němž má být makro vyhodnoceno. V takovém případě pak Zabbix nahradí makro hodnotou podle toho, kterému kontextu makra odpovídá (rovnost řetězců nebo splnění regulárního výrazu). Pokud kontext neodpovídá žádnému z definovaných, je využita výchozí hodnota makra, tedy jakoby uživatel nepoužil kontext vůbec \cite{zabbix.docs}.

Pro lepší pochopení maker s kontextem uveďme příklad. Uvažujme, že uživatel definuje následující makra s hodnotami:

\begin{itemize}
    \item \texttt{\{\$HOSTNAME\}} -- \texttt{example.com}
    \item \texttt{\{\$HOSTNAME:server1\}} -- \texttt{s1.example.com}
    \item \texttt{\{\$HOSTNAME:regex:"server[2-9]"\}} -- \texttt{s2.example.com}

\end{itemize}

Všimněme si zároveň formátu názvu -- je obsažen ve složených závorkách, začíná znakem \texttt{\$}, je psán kapitálkami a kontext je oddělen dvojtečkou, případně řetězcem \texttt{:regex:}, jedná-li se o kontext vyjádřený regulárním výrazem. Kontext může být také obklopen uvozovkami. Následující seznam pak ukazuje, jak by byla vyhodnocena jednotlivá makra s různými kontexty:

\begin{itemize}
    \item \texttt{\{\$HOSTNAME\}} -- \texttt{example.com}
    \item \texttt{\{\$HOSTNAME:"server1"\}} -- \texttt{s1.example.com}
    \item \texttt{\{\$HOSTNAME:server8\}} -- \texttt{s2.example.com}
    \item \texttt{\{\$HOSTNAME:nesmysl\}} -- \texttt{example.com}
\end{itemize}

Kontext tak přidává makrům jistou míru dynamičnosti a jejich využití úzce souvisí s nízkoúrovňovým objevováním (\emph{low-level discovery}), jemuž se budeme věnovat později.

Hodnotu některých maker je při použití také možné transformovat pomocí \uv{makro funkcí} \cite{zabbix.docs}. Jejich použití je však poměrně omezené.

\subsection{Šablony}
Šablona je v systému Zabbix předkonfigurovaná množina různých jiných entit Zabbixu. Šablony slouží ke zjednodušení konfigurace hostů sdílejících shodné monitorované prvky (itemy). Šablona může být přiřazena k několika hostům a jeden host může mít přiřazených více šablon. Navíc lze šabloně přiřadit jiné šablony, čímž se vytváří hierarchie šablon. Entity, které šablony mohou obsahovat, zahrnují itemy, triggery, pravidla pro nízkoúrovňové objevování, jimž se budeme věnovat i nadále, a vizuální prvky jako grafy nebo \uv{nástěnky} (\emph{dashboards}) \cite{zabbix.docs}.

Zabbix nabízí několik předdefinovaných šablon, které pokrývají běžné případy monitorování, jako jsou například šablony pro monitorování serverů, síťových prvků, databází, cloudových služeb nebo aplikací. Uživatelé mohou samozřejmě vytvářet vlastní šablony, které odpovídají jejich potřebám.


\subsection{Item}
Pojem item byl představen v úvodu této sekce, v dalším si jej podrobněji rozeberme. Item (datový element) je základním prvkem monitorování v Zabbixu, který reprezentuje jednu metriku. Jakožto u stěžejní entity Zabbixu mají datové elementy širokou škálu možností konfigurace, která se zejména odvíjí od \emph{typu} datového elementu. Základní možnosti jejich nastavení zahrnují název, klíč, jednotku metriky a zmíněný typ. Název je textový řetězec, který může obsahovat makro; jednotka také může být libovolný textový řetězec, avšak Zabbix umožňuje u některých známých jednotek úpravu formátu hodnoty. Například hodnotu v sekundách (jednotka \texttt{s}) převádí na řetězec specifikující počet let, měsíců, dní, hodin, minut, sekund a milisekund.

Klíč slouží jednak jako jednoznačný identifikátor datového elementu v rámci daného hosta či šablony a jednak pro určení, jaká data (metriky) má element sbírat. Zabbix specifikuje mnoho různých použitelných klíčů pro různé typy datových elementů. Název klíče může obsahovat čísla a písmena, podtržítka, tečky a spojovníky. Za názvem se často objevují parametry oddělené čárkou v hranatých závorkách, které dále specifikují sbírané metriky. Některé parametry je možné vynechat pro nastavení parametru na výchozí hodnotu. Jako parametr je možné poskytnout makro. 

Jako příklad uveďme klíč \texttt{net.if.out} dostupný pro typ \uv{Zabbix agent} (sbírá data z agenta Zabbixu). Klíč reprezentuje statistiky odchozího provozu síťového rozhraní. Zabbix k tomuto klíči specifikuje jeden povinný a jeden volitelný parametr: povinný specifikuje konkrétní síťové rozhraní monitorovaného uzlu (hosta), zatímco volitelný vybírá metriku -- počet bytů (výchozí nastavení), počet paketů, počet chyb atp. Item typu Zabbix Agent s klíčem \texttt{net.if.out[eth0,packets]} tak sbírá počet odchozích paketů na síťovém rozhraní \texttt{eth0}.

Typy itemů jsou rozsáhlé téma a dedikujme jim tedy svou vlastní sekci.

\subsection{Typy entity Item}

Již můžeme tušit, že typ datového elementu určuje způsob sběru metrik a jeho dodatečnou konfiguraci. Rozeberme tedy některé typy, které by se mohly zdát užitečné.

\subsubsection{Zabbix Agent a aktivní Zabbix Agent}
Základním typem je v předešlém příkladu použitý Zabbix Agent, u nějž Zabbix Server komunikuje s komponentou Zabbix Agent běžící na monitorovaném uzlu. Tomuto typu musí být dále specifikováno \emph{rozhraní} sloužící jako lokátor Zabbix Agenta v síti (IP adresa nebo DNS název a port). Ze zjevných důvodů je tento typ itemu nevhodný pro monitorování Lambda funkcí, jelikož nejsme schopni na serveru, na němž funkce běží, nainstalovat a provozovat agenta. Dalším nabízeným typem datových elementů je aktivní Zabbix Agent, kde je narozdíl od předchozího typu spojení se Zabbix Serverem navazováno agentem (komponentou). Aktivní agent v našem případě může být alespoň teoreticky užitečný, pokud bychom jeho protokol implementovali v transformační Lambda funkci posílající metriky z AWS CloudWatch do systému Zabbix.

Aktivní komunikaci zahajuje agent zprávou, v níž žádá o klíče datových elementů, jež má monitorovat. Tato počáteční zpráva obsahuje název \emph{síťového uzlu} (host), který je jedinečný pro daný Zabbix Server. V odpovědi serveru se pak nachází všechny klíče datových elementů daného síťového uzlu. Dále posílá agent zprávy obsahující kolekci objektů, jež zahrnují tentýž název síťového uzlu, klíč datového elementu a jeho hodnotu. Jednoduchost tohoto protokolu tak dále nabádá k jeho implementaci v Lambda funkci.

\subsubsection{Zabbix Trapper}
Pro nás zajímavým typem datových elementů je Zabbix Trapper, který umožňuje posílat data do Zabbixu z vnějších zdrojů. Ve své podstatě je Zabbix Trapper velmi podobný aktivnímu Zabbix agentovi, akorát komunikační protokol je ještě snazší. Očekávaný způsob použití tohoto typu je s pomocí softwarového nástroje zabbix sender, který pouze implementuje protokol Zabbix Trapper. 

V rámci protokolu komunikaci iniciuje \uv{Zabbix Sender} (klient) implementující protokol Zabbix Trapper. Namísto dvou fází však klient již od začátku posílá serveru nebo proxy přímo zapisované metriky identifikované názvem síťového uzlu a klíčem datového elementu. Tento protokol by tak byl pro implementaci v transformační Lambda funkci vhodnější než protokol aktivního Zabbix agenta.

Další výhodou tohoto typu je arbitrárnost klíčů itemů -- Zabbix Trapper nespecifikuje předem definované klíče, jelikož jsou uživatelsky iniciované, a tak poskytuje volnost ve vlastním formátu klíče. Klíč datového elementu je akorát nutné specifikovat v zasílané zprávě, aby bylo možné metriky správně přiřadit.\footnote{Tato skutečnost platí i v předchozím návrhu s implementací protokolu aktivního Zabbix Agenta.}

\subsubsection{HTTP/S Agent}
Další typ datových elementů, HTTP Agent (schopný komunikovat i přes protokol HTTPS), implementuje komunikaci se Zabbix Serverem pomocí HTTP/S rozhraní (nejčastěji REST API, avšak typ itemu je kompatibilní s libovolným přístupem). HTTP agent je dodatečně konfigurován pomocí URL koncového bodu rozhraní, parametrů v URL, typem HTTP dotazu, případně jeho tělem a hlavičkami. HTTP Agent navíc umožňuje povolit \uv{trapping}, čímž se zpřístupní všechny možnosti Zabbix Trapper itemu, tedy zejména posílat metriky Zabbix Trapper protokolem zevnějšku. Dotazy na koncový bod jsou posílány ve specifikovaných intervalech Zabbix Serverem nebo Proxy, jedná se tak o \uv{bezagentový} přístup, jelikož na uzlu poskytujícím rozhraní nemusí být doinstalován žádný pro Zabbix specifický software.

V našem případě by bylo oproti předem navrhovaným přístupům přiliš obtížné implementovat takové HTTP rozhraní. HTTP agenta bychom však mohli nakonfigurovat, aby volal REST API služby AWS CloudWatch, které umožňuje dotázat se na specifickou metriku. Díky tomuto přístupu bychom dokonce nepotřebovali jakoukoliv doposud navrženou architekturu na straně AWS -- tedy MetricStream, Firehose a transformační Lambda funkci -- jelikož bychom mohli využít přímo veřejné rozhraní AWS CloudWatch pro dotazování se na metriky vybraných Lambda funkcí.

Volba HTTP agenta by však přinášela několik problémů a nevýhod oproti datovým elementům typu Zabbix Trapper. HTTP agent není dobře škálovatelný, jelikož Zabbix Server, případně Proxy, musí dotazovat všechny koncové body, což může způsobit zbytečnou zátěž na serveru nebo proxy. Dále je nutné zajistit autentizaci a autorizaci Zabbix Serveru nebo Proxy vůči AWS REST API. 

Hlavní nevýhodou pak je \emph{zbytečné} dotazování na metriky funkcí, které v daném dotazovacím intervalu nebyly spuštěny. U datových elementů typu Zabbix Trapper můžeme v transformační Lambda funkci posílat metriky pouze, když je to nutné (t.j. pouze nově získané metriky od jejího posledního volání). Další nevýhodou je nutnost konfigurace monitorování daných Lambda funkcí v Zabbixu a ne na straně AWS bez dodatečných komponent v AWS. Vývojář Lambda funkcí by tak musel mít znalost Zabbixu a ručně konfigurovat monitorování svých funkcí v systému Zabbix. U předchozího přístupu stačí označit Lambda funkci ve službě AWS Lambda -- vývojář tak pouze potřebuje znát formát značení, jejž si představíme později v kapitole \ref{ch:impementace}, a nemusí se starat o konkrétní monitorovací systém; tuto starost řeší transformační Lambda funkce.

Mezi nevýhody také patří účtování za volání AWS REST API, které by mohlo být v případě velkého množství monitorovaných funkcí vysoké. Volání transformační Lambda funkce sice také stojí finanční zdroje, na druhou stranu v jednom jejím volání je žádoucí poslat všechny metriky v jednom dotazu. HTTP agenti by naopak periodicky dotazovali metriky pro každou jednotlivou Lambda funkci zvlášť (pro tu funkci, již by každý agent monitoroval izolovaně).

\subsection{Host a host group}
Host (síťový uzel) v Zabbixu reprezentuje jeden monitorovaný objekt. Prakticky můžeme hosta přirovnat ke \emph{jmennému prostoru} u AWS služby CloudWatch, jelikož slouží k seskupení metrik (datových elementů), alarmů (\emph{spouštěčů}) a dalších entit, z nichž pro nás později důležitá budou \emph{pravidla pro nízkoúrovňové objevování}. 

Při konfiguraci entity host je nutné specifikovat jeho název, který musí být unikátní v rámci Zabbix Serveru, a skupiny síťových uzlů, do nichž bude host zařazen. Dále je možné dodat zobrazovaný název, zda je host monitorován pomocí Zabbix Proxy (nebo přímo pomocí Zabbix Serveru) a několik \emph{rozhraní}, která jsou však relevantní pouze pro některé typy datových elementů s pasivním přístupem monitorování, jimž se dále věnovat nebudeme\footnote{Nejvhodnější je Zabbix Trapper, u nějž se jedná o aktivní přístup, případně typ HTTP agent, pro který je rozhraní irelevantní, i když povinné.}. Dále je možné přiřadit síťovému uzlu šablony, makra a další konfigurace \cite{zabbix.docs}. Vytvořenému síťovému uzlu lze ve webovém rozhraní nebo pomocí Zabbix API přidat datové elementy, spouštěče, grafy, pravidla pro objevování a další. 

Skupiny síťových uzlů pouze slouží k organizaci a nemají žádný vliv na monitorování. Skupině může být přiřazen libovolný počet šablon, které se automaticky přiřadí všem síťovým uzlům v dané skupině. Entita Host může být zařazena do více skupin \cite{zabbix.docs}.

\subsection{Trigger}
Trigger (\uv{spouštěč}) je v Zabbixu entita hlídající \emph{normální} hodnoty metrik podle určitého logického výrazu. Slouží jako alarm při problémových hodnotách metrik -- interně se může nacházet v jednom ze stavů \uv{OK} nebo \uv{PROBLEM} v závislosti na vyhodnocení daného logického výrazu (nepravdivý, resp. pravdivý).

Trigger je vytvářen v rámci hosta nebo šablony. V konfiguraci mu je přiřazen název, zobrazovaný název, \emph{severita}, \emph{logický výraz}, \emph{závislosti} na jiných spouštěčích a další. Severita určuje závažnost problému, který spouštěč hlídá. Základními severitami jsou \emph{informace}, \emph{upozornění}, \emph{průměrná} a \emph{vysoká severita} a \emph{katastrofa}. 

Logický výraz je složitější textová konstrukce, která může obsahovat několik podmínek, logické, aritmetické a porovnávací operátory, funkce a konstanty. Proměnné figurující ve výrazech jsou datové elementy identifikované názvem síťového uzlu nebo šablony, pod něž datový element spadá, a jejich klíčem -- je tedy možné vytvářet spouštěče, které hlídají hodnoty metrik různých \emph{síťových uzlů} nebo šablon. 

Funkcí v logických výrazech poskytuje Zabbix mnoho, jejichž seznam je dostpuný v dokumentaci. Zabbix dělí funkce do několika kategorií, jako jsou agregační funkce, matematické funkce, funkce pro práci s textem, funkce pro práci s datem a další. Hodnota funkce závisí na vstupních argumentech specifikovaných dokumentací. Mezi parametry se často objevují právě identifikátory datových elementů. Příkladem nechť jsou funkce \texttt{last()} a \texttt{avg()}. Funkce \texttt{last(<item>)} vrací poslední hodnotu metriky datového elementu v parametru, zatímco \texttt{avg(<item>,<interval>)} vrací průměrnou hodnotu metriky za určitý časový interval. Formát argumentů je dokumentován a prozatím se jím nebudeme zabývat. V některých případech může být argumentem i výraz.

Hodnoty funkcí lze upravovat standardními aritmetickými operacemi sčítání, odčítání, násobení, dělení a unárním mínusem. Porovnávací operátory slouží k porovnávání hodnot funkcí nebo konstant, jedná se o operátory \uv{rovná se}, \uv{menší než} atp. Výsledkem porovnávacího operátoru je hodnota 1 při pravdivém porovnání, jinak nula; dají se tedy použít i jako výraz. Logické operátory pracují s pravdivostními hodnotami pravda (1) a nepravda (0) běžným způsobem. Výsledkem celého výrazu zjevně musí být pravdivostní hodnota dosažitelná porovnávacími nebo logickými operátory.

U vytvořených spouštěčů je pravdivost výrazu vyhodnocována, když systém Zabbix obdrží nová data pro kterýkoliv datový element použitý ve výrazu. Po vyhodnocení je jednak aktualizován stav spouštěče -- pokud je výraz pravdivý, je spouštěč ve stavu \uv{PROBLEM}, jinak ve stavu \uv{OK}\footnote{toto chování lze však ovlivnit, my jej však pro jednoduchost zanecháme} -- a jednak se Zabbix Server rozhodne, zda vygeneruje interní \emph{událost} (\emph{event}) typu \uv{PROBLEM} nebo \uv{OK}. Událost \uv{PROBLEM} je generována při přechodu ze stavu OK spouštěče do stavu PROBLEM nebo (volitelně) při každém vyhodnocení výrazu jako pravdivého. Tato událost v systému setrvává, dokud systém nevygeneruje příslušnout událost typu \uv{OK}, která vzniká primárně při změně stavu spouštěče na OK\footnote{Událost OK lze generovat i manuálně ve webovém rozhraní, pokud je to u spouštěče povoleno.}. Projevem události \uv{PROBLEM} je zobrazení chyby ve webovém rozhraní (na \emph{nástěnce}) a případně zaslání notifikací, jimž se věnovat nebudeme.

Konfigurace entity trigger dovoluje specifikovat závislosti na jiných spouštěčích. Dokud se některý spouštěč v nachází ve stavu PROBLEM, pak všechny na něm závislé spouštěče do tohoto stavu nepřejdou. Tato vlastnost například umožňuje vytvořit více odstupňovaných spouštěčů tak, aby při problému spouštěče s vyšší severitou nebyl systém zahlcen událostmi od spouštěčů s nižší severitou, což v důsledku zvýší také přehlednost (na nástěnce se problém objeví pouze jednou a to s tou nejvyšší severitou).

Ve vztahu k monitorovacímu systému AWS Lambda funkcí jsou spouštěče konfigurovatelným prvkem -- jejich specifikaci tak určitým způsobem (navrženo dále v kapitole \ref{ch:impementace}) musí dodat uživatel. 

\subsection{Discovery}

Důležitou kapitolou v analýze systému Zabbix je funkcionalita \emph{objevování} (\emph{discovery}), která se dělí do tří kategorií. První dvě kategorie se zabývají automatickou registrací pasivních a aktivních komponent Zabbix Agent. Poslední kategorií je \emph{nízkoúrovňové objevování} (\emph{Low-level discovery}). Jelikož systém nebude využívat komponenty Zabbix Agent, jsou pro nás první dvě kategorie irelevantní a v dalším tak budeme pojmem objevování v kontextu Zabbixu mínit právě nízkoúrovňové objevování.

Funkce objevování umožňuje automatické vytváření některých entit pomocí \emph{pravidel pro nízkoúrovňové objevování} a \emph{prototypů entit} (\emph{prototype}). Entitami mohou být datové elementy, spouštěče a grafy, i když referenční materiály pro Zabbix API definují prototypy síťových uzlů, jež však nejsou dokumentovány. Pravidla pro objevování jsou další entity, které specifikují, jakým způsobem je objevování realizováno. Pravidla mají mnoho společných vlastností s datovými elementy a je také možné je vnímat jako datové elementy s tím rozdílem, že nemonitorují metriky, ale sbírají data o objevovaných entitách.

Pro účely této práce je objevování zjevně velmi žádoucí, jelikož díky němu nebude potřeba každou nově monitorovanou Lambda funkci potřeba zavádět ručně do systému Zabbix. To usnadní usnadní správu monitoringu a zvýší jeho přehlednost, což vyhovuje požadavkům zákazníka. Prozkoumejme tedy hloubějí možnosti nízkoúrovňového objevování.

\subsubsection{Pravidla pro nízkoúrovňové objevování}

Jak již bylo naznačeno, pravidla pro objevování jsou v podstatě datové elementy shraňující informace o objevovaných entitách, jež vytvoří na základě jejich prototypů. Pravidla se vytvářejí v rámci \emph{síťového uzlu} nebo \emph{šablony}. Základní konfigurace pravidla zahrnuje název, typ pravidla, klíč pravidla a další položky. Podobně jako u datových elementů typ pravidla určuje, jakým způsobem jsou data o objevovaných entitách získávána a klíč pravidlo jednak identifikuje a jednak u předem definovaných klíčů specifikuje, které entity jsou objevovány. Například pravidlo typu \uv{Zabbix agent} s klíčem \texttt{net.if.discovery} objevuje všechna síťová rozhraní monitorovaného uzlu. Pro nás prakticky využitelným typem pravidla je opět \uv{Zabbix trapper} ze stejných důvodů jako u datových elementů. Pravidlům tohoto typu je třeba posílat data o objevovaných entitách externě protokolem Zabbix Trapper, pouze na místo metrik jsou posílány informace o entitách, jejichž formátu se budeme věnovat později.

Důležitou konfigurací je také \emph{doba zanechání ztracených zdrojů} (\emph{keep lost resources period}), která specifikuje, po jak dlouhou dobu Zabbix Server ponechá vytvořené entity z jejich prototypů poté, co přestane obdržovat zprávy o daných objevovaných entitách. Doba je vyhodnocována při každém zpracování přijaté zprávy o objevovaných entitách. Jestliže doba od posledního \uv{objevení} (t.j. přijetí zprávy obsahující danou entitu) je větší než doba zanechání ztracených zdrojů a zároveň se daná entita v příchozí zprávě nevyskytuje, pak jsou entity odstraněny. Existence této konfigurace prakticky říká, že je třeba posílat informace i o již objevených entitách a nejen o nových; entity nestačí objevit jen jednou. U monitorování Lambda funkcí je tato konfigurace výhodná při rušení monitoringu Lambda funkce -- pro zrušení stačí přestat posílat zprávy o Lambda funkci a Zabbix Server po uplynutí doby zanechání ztracených zdrojů entity funkce automaticky odstraní. Znamená to ale však také, že bude potřeba do Zabbixu posílat informace o všech monitorovaných funkcích.

Dále je u pravidel možné specifikovat další typ maker, \emph{makra nízkoúrovňového objevování} (\emph{LLD macros}), která se používají pro dynamické vytváření objevovaných entit z prototypů. Formát těchto maker je stejný jako u ostatních maker v Zabbixu, pouze se místo znaku \texttt{\$} používá znak \texttt{\#}. Makra mohou být použita v konfiguraci prototypů entit a také v \emph{kontextu maker} pro dynamickou \uv{změnu} hodnoty makra u určitých entit. Hodnoty LLD maker jsou specifikovány ve zprávách posílaných pravidlům nízkoúrovňového objevování: při doručení zprávy do pravidla najde Zabbix Server všechny prototypy entit, v nichž se doručená makra vyskytují, a vytvoří z nich objevované entity s nahrazenými hodnotami LLD maker. V konfiguraci pravidel je však makra nutné poskytnout jen pro zpracování příchozí zprávy v jiném než standardním formátu. Pokud je použit standardní formát, makra není potřeba pravidlům přiřadit, neboť jsou automaticky zpracována Zabbix Serverem.

V neposlední řadě je u pravidel nízkoúrovňového objevování možné nakonfigurovat \emph{filtry} a \emph{přepsání pravidel} (\emph{overrides}). Filtry umožňují z objevovaných entit v příchozí zprávě vytvářet pouze entity (podle jejich prototypů) vyhovující specifikovaným požadavkům na hodnoty LLD maker, například pokud příchozí LLD makro splňuje regulární výraz. Přepsání pravidel umožňuje změnit některé vlastnosti entit od vlastností jejich prototypů na základě podobných požadavků jako u filtrů. Případem použití může být změna severity spouštěče -- u prototypu spouštěče není možné nastavit severitu pomocí LLD makra (musí být nastavena staticky) a pro její změnu je tedy nutné použít přepsání pravidel. Přepsání pravidla může být několik a jsou vyhodnocována ve zvoleném pořadí. 

\subsubsection{Prototypy entit}
Prototypy entit slouží jako vzory pro vytváření objevovaných entit. Prototypy entit jsou vytvářeny v rámci \emph{pravidla nízkoúrovňového objevování} a obsahují všechny vlastnosti, které mohou mít standardní entity. Ve vyplňovaných polích je však možné používat \emph{LLD makra}, která jsou nahrazena hodnotami při vytváření objevovaných entit, a to také jako kontext uživatelských maker. Entitami mohou být datové elementy, spouštěče, grafy a (neoficiálně) síťové uzly. U prototypů datových elementů a spouštěčů je navíc možné zvolit, zda se objevovaná entita z prototypu má tvořit a zda se má tvořit v \uv{aktivním} stavu. Tuto konfiguraci je možné měnit v přepsáních nízkoúrovňových pravidel a je tak možné například selektivně nevytvářet objevované entity podle specifických požadavků na hodnoty LLD maker.

\subsection{Modelování Lambda funkcí}
% jak namodelovat Lambdu / namapovat na Zabbix věci
% All in one host -- jeden host na všechny Lambda funkce, pomocí taggů
% Single host per Function, single trigger per Metric -- priorita funkce se přímo mapuje na severitu
% Single host per Function, multiple triggers per Metric -- odstupňování severity -- např. postupně vyšší hodnoty metriky mají větší severity (lambda trvá 500 ms = average, 1000 ms = disaster atp.)
Z předešlých sekcí máme dost znalostí o systému Zabbix a Lambda funkcích, abychom mohli začít modelovat monitorování Lambda funkcí v Zabbixu. V této sekci se budeme věnovat několika již navrženým možnostem, jak reprezentovat Lambda funkce v Zabbixu, a zpětně zvážíme jejich výhody a nevýhody.\footnote{Návrhy byly realizovány během vývoje systému, který předcházel vyhotovení tohoto textu, a proto o jejich vývoji budeme hovořit v minulém čase.}

Před představením samotných návrhů je třeba si utříbit a zrekapitulovat souvislosti a možnosti systému Zabbix. Atomickými entitami jsou entity Item, které reprezentují metriku, a Trigger, které sledují hodnoty metrik. Lambda funkce však nemůže být reprezentována jedinou entitou Item, jelikož metrik Lambda funkce můžeme sledovat mnoho -- například počet volání, doba trvání, velikost paměti, počet chyb atp. Výběr monitorovaných metrik navíc musí poskytnout uživatel systému a tyto metriky odpovídají entitám Item, případně jejich prototypům. S tímto \uv{omezením} bylo tedy nutné pracovat a vytvořit nějaký model monitorování Lambda funkcí, který je dostatečně obecný a zároveň je schopen reprezentovat všechny potřebné metriky.

\subsubsection{Model \uv{Vše v jednom}}
Prvotní model nepočítal s nízkoúrovňovým objevováním, kvůli čemuž postrádal možnost dynamického vytváření entit a v důsledku tak přehlednost, snadnou správu a konfigurovatelnost; položil však základy pro další modely. Prvnotní model byl jako všechny nadcházející konstituován z jednoho \emph{síťového uzlu}, narozdíl od dalších však obsahoval za každou požadovanou metriku pouze jeden \emph{datový element} typu \uv{Zabbix trapper} a jeden \emph{spouštěč}: datových elementů a spouštěčů bylo tedy tolik, kolik bylo monitorovaných metrik. Datové elementy monitorovaly svou metriku pro \emph{všechny} Lambda funkce a metriky Lambda funkcí tak byly \uv{roztroušeny} přes více datových elementů. 

Jelikož však všechny Lambda funkce sdílely pro své metriky shodné datové elementy v Zabbixu, bylo potřeba rozlišit, které hodnoty patří které funci. U spouštěčů rozlišování bylo docíleno pomocí \emph{značek} (\emph{tags}) a \emph{korelační značky} (\emph{correlation tag}), jimiž jsme se v analýze nezabývali. Značka je dvojice názvu a hodnoty přiřazená při tvorbě spouštěče, hodnota však může obsahovat makro, které Zabbix dokáže nahradit hodnotou sledovaného datového elementu, kterou lze dále upravit \emph{funkcí makra} (například nahradit podle regulárního výrazu). Korelační značka je pak název jedné z definovaných značek spouštěče. Při její specifikaci pak spouštěč dokáže generovat odlišné události označené touto značkou (a její hodnotou) pro odlišné hodnoty značky. Pokud se v hodnotě datového elementu objevuje název Lambda funkce, je tak možné generovat problémové události pro každou Lambda funkci zvlášť\footnote{Název funkce je třeba získat z hodnoty metriky např. pomocí náhrady podle regulárního výrazu. Číselnou hodnotu metriky je nutné extrahovat podobným způsobem, akorát ve výrazu spouštěče namísto v korelační značce.}. 

Model byl pracovně nazván \uv{Vše v jednom}, jelikož každý datový element reprezentující specifikovanou metriku zahrnoval všechny Lambda funkce.

Tento model však představoval značné nedostatky a to zejména v přehlednosti a konfigurovatelnosti spouštěčů. Jelikož shodná metrika všech Lambda funkcí sdílela jeden spouštěč, nebylo možné nastavit problémové hodnoty metrik pro jednotlivé funkce a stejně tak pro ně nebylo možné nastavit různé severity. Přehlednost trpěla tím, že jeden datový element sbíral metriky různých funckí. Model tak byl značně nevyhovující. 

\subsubsection{Model \uv{Jeden item, jeden trigger}}

Další model rozšiřuje funkcionalitu předchozího zejména přidáním nízkoúrovňového objevování. Pro každou poskytnutou metriku není v Zabbix serveru vytvořen datový element, nýbrž jeho prototyp, a stejně tak pro spouštěče. Skutečné datové elementy jsou z prototypů vytvářeny pro každou objevenou Lambda funkci -- pravidlo objevování získá data o monitorovaných Lambda funkcích a z nich vytvoří objevované entity. V Zabbixu je tak funkce opět roztroušena přes více datových elementů (jeden element na monitorovanou metriku), ale zároveň datové elementy nesdílí více funkcí. Funkce je tak reprezentována množinou \emph{výhradně svých} datových elementů a spouštěčů. Veškeré entity (pravidla, prototypy, objevované datové elementy a spouštěče, makra) jsou vytvářeny v rámci jednoho \emph{síťového uzlu}.

Každá funkce a její metrika má tedy svůj jediný datový element a spouštěč, pročež byl pracovně pojmenován \uv{Jeden item, jeden trigger}.

Dalším posunem od modelu \uv{Vše v jednom} je zavedení \emph{priorit} Lambda funkcí. Priorita funkce hraje podobnou roli jako severita spouštěče a určuje abstraktní třídu, do níž funkce spadá. Třídou je primárně myšlena kritičnost funkce a intuitivně i severita spouštěče hlídajícího její metriky, avšak je možné priority vnímat i jako jiné klasifikace, například třídy doby trvání funkcí, přičemž rychlejší funkce nemusí znamenat kritčtější. Pro jednoduchost však uvažujme kritičnost/důležitost funkce. Priorita může nabývat hodnot 0 až 4 a speciální hodnoty -1 reprezentující neznámou prioritu. Priorita je uložena externě (v proměnné prostředí Lambda funkce na straně AWS) a pro každou funkci volena uživatelem. Do systému Zabbix musí být poslána jako součást dat pro objevení spolu s názvem funkce.

V rámci modelu \uv{Jeden item, jeden trigger} je priorita mapována na dvojici severity spouštěče a \emph{konstanty}, vůči níž je hodnota metriky spouštěčem porovnávána. Konfigurace metrik poskytnutá uživatelem obsahuje tabulku přiřazující každé prioritě takovou dvojici. Při objevení Lambda funkce je vytvořen datový element pro každou metriku a spouštěč s odpovídající severitou, která je nastavena pomocí přepsání pravidla nízkoúrovňového objevování a přijaté priority funkce. Konstanta je ve výrazu spouštěče reprezentována uživatelským makrem s kontextem makra, který je s využitím LLD makra značící prioritu doplněn hodnotou dané priority. Každá metrika tak musí mít u síťového uzlu definována makra s kontextem pro všechny možné priority.

Pro komplexitu slovního popisu uveďme příklad. Uvažujme Lambda funkci pojmenovanou \uv{MojeFunkce} s prioritou 3. Jediná specifikovaná metrika je \uv{Doba trvání}, která sbírá odpovídající metriky z AWS CloudWatch. V tabulce priorit je priorita 3 mapována na dvojici \emph{vysoká severita} a konstantu 1000 (jednotky milisekund). Do nakonfigurovaného Zabbix serveru jsou pak eventuálně pravidlu pro nízkoúrovňové objevování zaslána data obsahující záznam s názvem funkce a prioritou:

\begin{verbatim}
[
    ...,
    {
        "{#FN_NAME}": "MojeFunkce",
        "{#PRIO}": 3
    },
    ...
]
\end{verbatim}

Záznam nese LLD makra pro název funkce a prioritu, respektive. Z těchto informací Zabbix server vytvoří datový element pro Lambda funkci měřící metriku \uv{Doba trvání} a spouštěč severity \emph{vysoká} s výrazem, který poronvává poslední hodnotu metriky s konstantou danou makrem \texttt{\{\$DOBA_TRVANI:3\}\}. Během konfigurace Zabbix serveru bylo centrálnímu síťovému uzlu přiřazeno toto makro s hodnotou 1000 (podle tabulky v konfiguraci metriky). Pro makro \texttt{\{\$DOBA_TRVANI\}} existují kontexty se všemi prioritami dle tabulky priorit v konfiguraci metriky. Severita spouštěče je nastavena pomocí přepsání pravidla nízkoúrovňového objevování, které specifiuje, že pokud LLD makro \texttt{\{\#PRIO\}} nabývá hodnoty 3, pak je severita spouštěče \emph{vysoká}. Každá priorita v tabulce priorit má své přepsání pravidla.

Pokud po objevení funkce objevený datový element přijme hodnotu vyšší než 1000, spouštěč vygeneruje problémovou událost s vysokou severitou.

Model \uv{Jeden item, jeden trigger} je tak výrazným posunem od modelu \uv{Vše v jednom}, avšak stále nebyl dostatečně uspokojivý. Přestože model umožňuje nastavovat priority funkcí a nakonfigurovat tak, jak závažné problémy funkce generují při překročení kterých hodnot, trpí nedostatečným množstvím problémových stavů: model Lambda funkce buď negeneruje žádný problém, anebo generuje problém s nastavenou severitou a je tak nutné zvolit jedinou mezní hodnotu určující problémový stav. V reálném nasazení je však žádoucí odstupňovat severity podle závažnosti problému -- prakticky tedy vytvářet více spouštěčů různých severit a při nižších mezních hodnotách metriky generovat problém s nižší severitou. Dalším nedostatkem modelu je \uv{konstantní} priorita Lambda funkce vůči všem sbíraným metrikám. Například metrika doby trvání Lambda funkce nemusí mít pro danou funkci takovou váhu, jako počet chyb. Oba tyto nedostatky byly řešeny v následujícím modelu.

\subsubsection{Model \uv{Jeden item, více triggerů}}

Další model se od předchozího neodlišuje takovým způsobem jako předchozí od původního. Hlavní změna přichází v tabulce priorit při konfiguraci metriky a v počtu prototypů spouštěčů. Tabulka je od předchozího případu dvourozměrná, kde první dimenze (řádky tabulky) značí prioritu Lambda funkce a druhá (sloupce) severitu. Kombinace priority funkce a severity spouštěče je pak mapována na konstantu. Během konfigurace Zabbix serveru je pak pro každou metriku vytvořen jeden prototyp datového elementu a prototypy spouštěčů (potažmo) všech severit. Prototypy spouštěčů se liší pouze v severitě a v konstantě ve výrazu, která je opět vyjádřena makrem s kontextem (kterým je opět LLD makro priority Lambda funkce).

Jelikož v tomto modelu může mít každá severita spouštěče ve výrazu různé konstanty, je potřeba zvětšit také počet maker. V minulém modelu bylo vytvořeno pro každou metriku jedno makro a k němu kontext pro každou prioritu. Protože nový model uvažuje více spouštěčů, bude potřeba vytvořit makro pro každou kombinaci metriky a severity a makru této kombinace přiřadit kontext pro každou prioritu. Z příkladu v minulém modelu by tak pro spouštěč se severitou \emph{vysoká} název makra mohl vypadat následovně: \texttt{\{\$DOBA_TRVANI_HIGH:3\}}. Priorita 3 byla opět zjištěna z hodnoty LLD makra \texttt{\{\#PRIO\}}.

Změnu bylo třeba provést také u přepsání pravidel. V tomto případě spouštěčům severity neměníme, neboť prototypy se všemi severitami již existují, ale můžeme volit, zda konkrétní spouštěče z prototypů vytvářet. Uživateli je umožněno vynechat některá pole tabulky priorit a severit, pokud si nepřeje u určitých priorit specifikovat všechny severity (například mu stačí pouze tři úrovně varování), a tak vypnout objevení spouštěčů odpovídajících prázdným kombinacím v tabulce.

Model mezi objevenými spouštěči dále zavádí závislosti: všechny objevené spouštěče s nižší severitou jsou závislé na spouštěčích se severitou vyšší u dané metriky a priority Lambda funkce.

Pro ilustraci opět uveďme příklad: uživatel nakonfiguroval metriku \uv{Doba trvání} s tabulkou priorit a severit jako v tabulce \ref{tab:multi-trig-prio_tab-example} a v AWS Lambda provozuje funkci \uv{MojeFunkce} s prioritou 3. Po zprovoznění vyvíjeného systému je funkce objevena (prozatím) stejným způsobem jako v minulém příkladu.

Při objevování Zabbix server na základě prototypů vytvořil jeden datový element pro metriku \uv{Doba trvání} Lambda funkce \uv{MojeFunkce} a podle poskytnuté tabulky dva spouštěče: jeden se severitou \emph{varování} a druhý s \emph{průměrnou} severitou. Konstanty ve výrazech spouštěčů jsou zastoupeny makry \texttt{\{\$DOBA_TRVANI_WARNING:3\}}, respektive \texttt{\{\$DOBA_TRVANI_AVERAGE:3\}}, jejichž hodnoty odpovídají hodnotám 750 a 1000 milisekund. Spouštěč se severitou \emph{varování} je navíc závislý na druhém spouštěči. Ostatní spouštěče (zbylých severit) pomocí přepsání pravidla nízkoúrovňového objevování nebyly vytvořeny, neboť je uživatel nepožadoval.

Pokud příkladový Zabbix Server přijme hodnotu metriky \uv{Doba trvání} dané funkce 800 milisekund, spouštěč se severitou \emph{varování} vygeneruje problémovou událost. Jestliže následně přijme hodnotu 1100 milisekund, problémovou událost generuje spouštěč s \emph{průměrnou} severitou a předchozí událost je díky závislosti spouštěčů uzavřena. V systému tak setrvává pouze událost s nejvyšší severitou.

Model \uv{Jeden item, více triggerů} dále řeší prioritizaci Lambda funkcí vůči jednotlivým metrikám. Minulý model zaváděl konstantní prioritu uloženou v proměnné prostředí Lambda funkce v AWS, tento model zavádí proměnnou prostředí, která obsahuje seznam dvojic identifikátoru metriky (jedinečný název poskytnutý v konfiguraci) a priority funkce vůči ní. Při objevení funkce je do Zabbixu poslán její název a každá z priorit jako LLD makra. Pravidlo nízkoúrovňového objevování tak přijímá ve zprávě více maker, na jejichž základu vytváří objevované entity. Zpráva tak může vypadat například následovně:

\begin{verbatim}
[
    ...,
    {
        "{#FN_NAME}": "MojeFunkce",
        "{#DOBA_TRVANI_PRIO}": 3,
        "{#POCET_CHYB_PRIO}": 1
    },
    ...
]
\end{verbatim}

Na základě těchto informací Zabbix server vytvoří dva datové elementy pro metriky \uv{Doba trvání} a \uv{Počet chyb} a několik spouštěčů pro každou metriku dle tabulky priorit a severit z konfigurace. Jediná změna oproti konstantním prioritám je v konstantě ve výrazech prototypů spouštěčů: konstanta je stále reprezentována makrem s kontextem odpovídajícím LLD makru, nově však LLD makro v kontextu odpovídá LLD makru metriky, které je přijato ve zprávě -- namísto např. 

\begin{verbatim}
{$DOBA_TRVANI_HIGH:{#PRIO}}
\end{verbatim}

se nyní na místě konstanty ve výrazu prototypu spouštěče nachází

\begin{verbatim}
{$DOBA_TRVANI_HIGH:{#DOBA_TRVANI_PRIO}}.
\end{verbatim}

Tento přístup lze dále upravit tak, aby bylo možné vybírat pouze specifické metriky pro každou Lambda funkci. Jestliže seznam identifikátorů metrik a jejich priorit v proměnné prostředí Lambda funkce neobsahuje identifikátory všech konfigurovaných metrik, objevovací zpráva nebude obsahovat jejich LLD makra a Zabbix server tak nebude vytvářet datové elementy a spouštěče těchto metriky pro dané Lambda funkce. Zabbix Server vytváří pouze ty entity, v jejichž prototypech se nachází LLD makra přijatá ve zprávě. Pokud se například ve zprávě nenachází LLD makro \texttt{\{DOBA_TRVANI_PRIO\}}, nebudou vytvřeny spouštěče pro danou metriku, neboť se LLD makro v prototypu spouštěče nachází, ale ve zprávě nikoliv. Datové elementy jsou vytvářeny vždy pro všechny metriky, neboť prototypy datových elementů neobsahují LLD makra pro priority, pouze pro název funkce. Monitorovány jsou tedy vždy všechny metriky, ale automaticky sledovány pouze zvolené.
